GLOSSARY

小白词典

OTel 的词第一次看会绕；先记住“树 + 节点 + 旁听者”三个就够。

OpenTelemetry
一套通用的追踪标准。它只负责“记录调用树”，不负责展示；Langfuse 是其中一种后端。
Trace / Span
trace 是一次完整调用；span 是树上的节点。一次 chat 是一棵 trace，模型调用、工具调用、阶段各是一个 span。
SpanProcessor
旁听者。span 开始/结束时收到通知，可以改属性、上传。3.2 在这里补 session。
TracerProvider
负责创建 span 的“总厂”。AI SDK 的 telemetry 通过全局 provider 产出 span。
AI SDK telemetry
SDK 自带的埋点开关。functionId 会变成根 span 的 gen_ai.agent.name。
Langfuse
专门看 LLM 调用树的系统：prompt、输出、工具、token、成本。
ALS
按异步调用链隔离的“隐形书包”。本地 trace id 放在里面，流式回调也能取到。
Bridge
业务与第三方库之间的插座。业务只认接口，实现启动时注入，测试不加载 OTel。
一次性 Map
取一次就删的临时表。避免长进程里按请求累积，越跑越大。

PORT · 01

bridge：业务只认插座，不认电厂

ChatService 不 import OTel/Langfuse；它只调用一个无依赖接口。真正的实现在启动时注入。

为什么先讲这个？3.2 最容易写坏的地方，是把 Langfuse/OTel 直接 import 进业务文件。那样测试 import ChatService 就会顺手加载 exporter，甚至注册全局 provider。bridge 把这件事挡在业务之外。

ASSEMBLY · 02

langfuse：OTel 装配与根 span

这里把 AI SDK 的 telemetry、Langfuse 的 exporter、以及“给根 span 补 session”的旁听者接在一起。

先补三个词：trace 是一次完整调用树，span 是树上的一个节点，SpanProcessor 是旁听者——span 开始/结束时它能收到通知，可以改属性，也可以上传。Langfuse 就是靠这棵树展示模型明细的。

01文件头：整条路径的规则3.2

L1–7

只由 index.ts 启动时调一次；三件套缺失只打 I_TRACE_EXPORT_DISABLED，本地 traces 照写；AI SDK 根 span 不设全局 active、要到流消费时才创建；ChatSpanProcessor 在 onStart 补 session；不打印 Key。

02导入清单3.2

L11–24

OTel 的 context/trace 与 TracerProvider；AsyncLocalStorageContextManager 让异步调用链上的 span 能找到父节点；LangfuseSpanProcessor 负责上传；LangfuseVercelAiSdkIntegration 是 AI SDK 的自动埋点；registerTelemetry 把它挂到 AI SDK。

03SdkSpan：为什么要强转3.2

L26–29

ChatSpanProcessor 需要读两个实现层字段：parentSpanContext（判断是不是根 span）和 attributes（读 gen_ai.agent.name）。OTel 的公开 Span 接口没有这两个字段，所以这里做一次窄化类型转换。

04两张 Map + 两个开关3.2

L31–35

Chats：本地 trace id → session id，根 span 到来时查它。TraceIds：本地 trace id → Langfuse trace id，流结束时取它。started/enabled 保证只装配一次，并记住是否启用。

05setup：只做一次，缺钥匙就退出装配3.2

L37–43

started 防重复；configured() 查三个 env。缺任何一个只打一行 I_TRACE_EXPORT_DISABLED 然后 return。注意：它不抛、不阻塞，本地 traces 公共行照写，/chat 照常工作。

06OTel 装配的五个动作3.2

L44–50

1）context.setGlobalContextManager(new AsyncLocalStorageContextManager())：让异步流里的 span 有正确的父节点。2）LangfuseSpanProcessor：上传。3）TracerProvider 挂两个旁听者：上传 + 补 session。4）trace.setGlobalTracerProvider：注册全局。5）registerTelemetry(LangfuseVercelAiSdkIntegration)：AI SDK 自动埋点。最后把实现注入 bridge。

07beginChat：先登记，后建 span3.2

L53–56

在 streamText 之前调用。它只做一件事：把 localTraceId → sessionId 放进 Chats。因为根 span 要到流被消费时才创建，所以必须提前登记，等它来时才有 session 可查。

08takeChatTraceId：取一次就删3.2

L58–65

从 TraceIds 取 Langfuse trace id；取到就同时删两个 Map。只能调一次：第二次会返回 undefined。这是有意的，避免进程长期运行 Map 无限增长。

09createStageSink：3.3 的入口3.3

L67–83

这段属于 3.3，但住在这个文件里。它给 retrieve 的 5 段各开一个 Langfuse span：startObservation(stage, {input}, {asType:"span", startTime})，update 写 output，失败标 ERROR，end(ended_at) 结束。因为 context manager 在，这些 span 会自动挂到当前 tool span 下。

10ChatSpanProcessor：抓根 span3.2

L85–100

onStart 只处理根 span：parentSpanContext 为空，且 gen_ai.agent.name === "chat"。然后从 ALS 取本地 trace id，从 Chats 取 session id；写 session.id、traceName、tags、metadata 里的 route/本地 trace id；最后把 spanContext().traceId 存进 TraceIds。

11其余生命周期：空实现3.2

L102–111

onEnd、shutdown、forceFlush 都不做事。上传交给 LangfuseSpanProcessor；我们只关心根 span 开始时补属性。

12configured：三件套3.2

L113–119

只判断 LANGFUSE_PUBLIC_KEY / LANGFUSE_SECRET_KEY / LANGFUSE_BASE_URL 是否存在且非空。不打印值，也不在这里发请求。

DECISIONS

六个设计选择

这些都是实测/踩坑之后定下来的，不是照抄官方示例。

01

业务不 import OTel

ChatService 只认 bridge。测试 import 它时不会加载 exporter，也不会注册全局 provider。实现只在 index.ts 启动时注入。

02

根 span 用 SpanProcessor 抓

官方示例的 propagateAttributes 对 streamText 不可靠：根 span 延迟创建，传 context 时它还没出现。改在 onStart 里认根 span，直接补 session。

03

session_id 早写 + COALESCE

流开始就写 session，流结束再写最终状态。两次 finishTrace 用 COALESCE，端点壳的 null 不会把 ChatService 写的值抹掉。

04

本地只留公共行 + 外链

prompt/回复/工具全文/token 全在 Langfuse；本地 traces 只是多填一个 langfuse_trace_id 的值（列在 3.1 已建）。避免两份数据、两种真相。

05

Map 取一次就删

takeChatTraceId 取到后同时删 TraceIds 和 Chats。每个请求只留一次，长进程不会越跑越大。

06

中断不落 assistant

半截回答只在界面上标“未完整”；库里只留孤立 user 消息。避免下轮历史把半截回答当完整上下文。

PITFALLS

容易踩的坑

3.2 的坑集中在“根 span 什么时候出现”和“两次收口谁覆盖谁”。

  • 别在业务里直接 import OTel/Langfuse。会让测试加载 exporter；用 bridge，实现只在启动时注入。
  • 别漏 telemetry.functionId。ChatSpanProcessor 靠 gen_ai.agent.name === "chat" 认根 span；没有它，session 补不上。
  • 别照抄 propagateAttributes。对 streamText 实测不可靠：根 span 延迟创建，传 context 时它还没出现。
  • 别把 setTraceSession 拖到流结束。流卡住/进程崩了，trace 就永远不知道属于哪个会话。
  • 别去掉 COALESCE。端点壳先收口会传 null；没有 COALESCE，它会把 ChatService 写的 session/langfuse id 抹掉。
  • 别打印 Key。写出侧只读 env 判断真假；读侧 Basic Auth 只在内存里拼，不落日志。
  • 别把 takeChatTraceId 调两次。它取一次就删，第二次返回 undefined。
  • Langfuse 不可达时别阻塞 chat。导出失败只影响远程；本地 traces 照写。Keys 在但服务不可达时，langfuse_trace_id 可能仍是 OTel trace id，而远端没有记录。
  • 进程崩溃时 onEnd 不一定跑。那一行会停在 running；这是已接受的代价，不是“数据被删”。
  • 别用 v3 traces API 读观测。/api/public/traces/{id} 已弃用；用 /api/public/v2/observations。
