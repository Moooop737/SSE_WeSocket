01先把请求体当 JSON 对象

L143–152

不是合法 JSON → 400 E_BAD_JSON；是合法 JSON 但不是对象（null/数字/数组）也 400。这一层不建 Resource：系统边界先挡住，后面的管线就不用到处判空。

02url 与 content 恰好给一个

L155–166

这是 1.2/1.3 共用入口：URL 分支归 1.2，content 分支归 1.3。纯空白 content 会被折成 undefined，单独报 E_EMPTY_CONTENT；两个都给或都不给报 E_AMBIGUOUS_INPUT。

03URL 只放行 http/https，然后组装配单

L171–184

new URL 先判语法，再判协议白名单；通过后把来源翻译成策略：fetcher: "http"、parser: "html"。这一步只组 Recipe 与 KBData，不发网络请求、不建行。

04content 分支是 1.3 的补丁1.3

L185–192

passthrough + text 让粘贴的 Markdown/纯文本跳过 fetch，直接进 parse→chunk→embed→write。列在这里是为了说明“同一个 POST 有两条来源”，不把它算成 1.2 的 URL 交付。

05调管线；sink 是 3.4 的观测补丁3.4

L194–203

factory.assemble(recipe).run(data, undefined, { sink }) 里的 sink 把每个 stage 的输入/输出/耗时写进 trace（3.4）。1.2 收口时这里是 run(data, c.req.raw.signal)；1.4 把取消改成服务端持有后，不再拿 HTTP 连接当信号源，所以第二个参数现在是 undefined。

06三种结果：409 / 422 / 201

L204–210

查重命中 → 409 E_DUPLICATE；建行后失败 → 422，body 带 resource（里面有 id/error_reason）；成功 → 201，带 resource、chunk_count，有 warning 就一起透传。当前 POST 是同步跑完才返回，所以 201 时已经是 ready，不需要前端轮询。

02查重只拦 ready / processing

L53–60

findActiveBySource 只匹配这两种状态，而且要求未软删；failed 的同 URL 允许重抓。命中时返回 resource: null，不会建行。这就是 1.2 选的幂等策略：拒绝，而不是更新。

03先建 processing 行，标题用域名占位

L62–70

为什么先建？因为 AC 要求“已进入入库后才失败”也要有一条 failed Resource 附原因；不先建行，fetch 失败就没有地方留痕。标题优先级是“用户给的 → parse 出的 → 域名占位”，这里先放域名，parse 成功后再回填。

04取消开关 + fail 留痕1.4

L72–84

1.4 把取消改成服务端持有：ctrl 按资源 id 登记，任意请求都能按；1.2 只要求入口支持信号。fail() 先删已写 chunk，再把行改成 failed 并写 error_reason；这里绝不复用取消信号，否则 aborted signal 会把“失败留痕”一起杀掉。

13 · DECISIONS & PITFALLS

关键取舍与踩过的坑

这些是“为什么长这样”的原因。否掉的方案也写出来，避免下一轮重新发明。

展开全部取舍与踩坑
D-01

工厂模型，而不是一个 runIngest

旧的 orchestration/ingest.ts 用一个大函数串所有段，来源分支和 stage 构造混在一起。build3 换成 Recipe→Factory→run/batch：工厂只兑换名字，来源→策略名的判断留在路由。代价是多一层类型与注册表，收益是 1.3 只换名字就能复用整条链。

D-02

先建 processing 行，再抓取

如果抓完才建行，fetch 失败就没有 Resource 可留痕，违背 AC“已进入入库后才失败 → 创建失败 Resource”。先建行的代价是：processing 行在 fetch 前就存在，需要启动清扫兜底（1.1）和取消/写守卫（1.4）。

D-03

幂等 = 拒绝，且只拦 ready/processing

同 URL 已有活跃资源 → 409 E_DUPLICATE，不建行；failed 允许重抓。没有数据库唯一索引，查重与建行之间有 TOCTOU 窗口（双击/并发可能双建），Lynx 2026-10-13 已定 P1 不加索引，接受该风险；这条不能写成“完全幂等”。uri.canonicalize() 尚未落地，当前按原文 URL 相等判重（epics.md 2026-10-24 对账）。uri.canonicalize() 尚未落地，当前按原文 URL 相等判重（epics.md 2026-10-24 对账）。

D-04

标题：用户 > parse > 域名占位

建 processing 时还没有 parse 结果，只能先用 hostname；parse 成功后若用户没给标题且标题不同，再回填。这样列表里不会长时间显示“未命名”，201 返回的也是真标题。

D-05

“空正文”与“0 块”是两条失败

parse 后 trim 为空 → 解析后无正文；正文非空但分块器过滤掉所有空白块 → 内容为空。两者都不进入 ready，但原因不同，排查时能区分是抓取/解析问题还是分块问题。

D-06

ready 放进写入事务

1.2 评审 P3 发现：先提交 chunk/向量、再单独改 ready，若第二步失败，下次启动清扫会把已成功的入库删掉。修法是把 UPDATE status='ready' 放进 writeChunksWithEmbeddings 的同一事务，端口注释写清“这个方法会一起转 ready”。

D-07

Signal 只喂长操作

fetch/embed 吃信号；fail() 改状态绝不复用同一个信号，否则取消时连“失败留痕”都被中断，行会卡在 processing。1.2 只留入口；1.4 才把 controller 登记到进程级 Map，并补写入后的取消复查。
