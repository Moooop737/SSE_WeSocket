01 · 结论与边界

这一格只做「钉住基线、并排数字」

不替人下结论：不判变好/退化，不画趋势图，也不把两次 run 的差异算成一个新分数。

01 / BASELINE

一个数据集一条基线

沿用 7.1 就有的 eval_datasets.baseline_run_id：换基线是显式动作，run 跑完只是候选。列上没有外键，删 run 的事务里顺手把基线清空。

02 / ADOPT

只接 done 的 run

PUT /eval/datasets/:id/baseline：数据集或 run 不存在 404，run 不属于该数据集 400，非 done 409。部分结果不配当基线。

03 / COMPARE

两列数字，不做判决

顶部并排两次 run 的总分；另给「相同条目 · N 条」平均（只算两次 run 都有的 case）。逐条按当前 run 的快照顺序，基线缺的显示 —。

04 / DELETE

运行删除 UI 补齐

右栏顶部两步确认（4 秒内再按才真删）；左侧 run 行本身是按钮，不在按钮里嵌按钮。运行中隐藏入口，后端仍 409 兜底。

不属于 7.3：判法一致性黄条 /「分数不可直接比」提示（Lynx 2026-10-29 改口径，取消）、变好/退化/新增/消失的 diff、趋势图、跨数据集对比（未排期）、gold 的前端挑选与编辑（7.4 / 未排期）、自动回归与 CI 门禁（后续）。

02 · 数据怎么流

基线 id 住在数据集行上，对照在浏览器里算

后端只负责「哪条 run 是基线」；两次 run 的数字都在各自的 results 里，对照不需要新接口。

写基线

  • 入口PUT /eval/datasets/:id/baseline
  • 守卫归属 400 · 非 done 409
  • 落库baseline_run_id

读对照

  • 基线GET /eval/runs/:baselineId
  • 当前detail（已加载）
  • 计算浏览器端 map + mean

删运行

  • 第一步装填 4 秒
  • 第二步DELETE /eval/runs/:id
  • 副作用baseline 清空
为什么不做对照接口：一次 run 的 results 本来就是整份 jsonb，拿两次已经足够；在服务端再算一遍只会多一份口径。聚合与交集平均都在 ComparePanel 里用同一份数据算。

06 · 取舍与坑

为什么不给「判法不一致」黄条

Lynx 2026-10-29 改口径：总分直接可比，题集差异用「相同条目平均」消化，而不是拦着不让比。

WHY TOTALS

总分并排 + 交集平均

两次 run 的总分先摆出来；如果 case 集合不同，再给只算交集的平均并标条数。既保留「全部 case」的口径，又给一个 apples-to-apples 的数。

NO VERDICT

不算变好/退化

不做 diff、不标红绿箭头、不算新增/消失。系统只摆事实，结论归人；这也让 7.4 引入 judge 后不需要推翻这里。

DONE ONLY

只有 done 能当基线

queued/running 还没有完整结果，failed/cancelled 是残卷；拿它们当基线会把后面的对照带偏。409 的话术直接说「只有完成的运行才能当基线」。

NO FK

基线列没有外键

7.1 定表时因循环 FK 会拖垮 drizzle 生成，baseline_run_id 没挂外键；删 run 的清理放在 7.2 的事务里做。代价：采纳与删 run 并发时有极小悬空窗口（单用户下接受）。

TWO STEP

删除要两下

删一条 run 会丢掉整份历史结果；两步确认与资源页的肌肉记忆一致。切 run 立即解除装填，4 秒后自动收回。

ORDER

顺序跟当前 run

对照的行序取当前 run 的 snapshot.cases，不取基线也不另排序；题集中途改过，历史 run 的对照顺序也不变。

踩坑：— 与「错误」都占一格；不要为了好看把缺失行隐藏掉——那会变成事实上的「消失」判定。另：基线 run 详情是额外一次 GET，删除/采纳后必须重拉数据集，否则徽标与对照对象会不同步。
