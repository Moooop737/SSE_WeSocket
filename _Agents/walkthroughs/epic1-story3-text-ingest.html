01

复用

粘贴/文件导入跳过网络抓取，但仍走 fetch → parse → chunk → embed → write：第一段换成零 I/O 的 PassthroughFetcher，第二段换成 TextParser，后三段与 URL 入库完全同一套代码。

02

两条内容拒绝

只在建 resources 行之前拒绝：body 解析失败或顶层不是对象 → E_BAD_JSON；content 是空白串 → E_EMPTY_CONTENT。内容质量的“不可读/编码异常”不在这里判。

03

前端接线

粘贴时用户自选 markdown / plaintext；选文件按后缀决定类型，accept 只收 .md / .markdown / .txt。后端只收到字符串，不猜类型。

GLOSSARY

小白词典

第一次读这套代码，先把这几个词对齐。

Markdown / plaintext
两种纯文本。P1 的处理路径完全相同；区别只在 resources.content_type 这个存档字段。
passthrough（直通）
一个不发请求的 Fetcher：把请求体里的正文原样放进 ctx.fetched，假装“抓取”已经完成。
parse（解析）
把抓取结果变成 { title, text }。HTML 走 HtmlParser；纯文本走 TextParser，正文不改。
chunk（分块）
把长正文切成可检索的小块，并记录 start_offset / end_offset；代码块、表格等保护段优先整块保留（超过 7500 字符的极端块仍会被强切）。
embed（向量化）
把每块正文交给 embedding 模型，得到一串数字向量；检索时用同一模型算提问向量。
Resource / processing / ready / failed
一条入库记录。建行时是 processing，写完后变 ready；建行后失败则变 failed 并带原因。
data_uri
内容来源标识。URL 入库直接用 URL；粘贴内容生成 urn:kc:paste:<uuid>，避免把整段正文塞进标识字段。
E_BAD_JSON / E_EMPTY_CONTENT
两条内容拒绝码：请求体不是合法 JSON 对象；content 是空白串。两者都不创建 Resource 行。
accept
文件选择框的过滤属性。它只是前端提示，不是安全边界；后端仍然只按“收到的是不是字符串”判断。

CHOICES

三条取舍与容易踩的坑

这一格真正“拍下来”的东西；实现细节之后可以改，这三条是口径。

01

共用 parse 分支，content_type 只存档

选择：markdown 与 plaintext 都走 TextParser，正文原样交分块器；content_type 写进 Resource 行，作为后续分支的预留位。否掉：给 Markdown 单独写一套语法解析/清洗——P1 不需要，而且 legacy 分块器已经保护代码块、表格、链接等结构。代价：纯文本里如果出现 Markdown 表格形状，也会被保护段当成表格；P1 接受。

02

不做“不可读 / 编码异常”启发式

选择：后端只判断“收到的是不是字符串、trim 后空不空”，不猜编码、不猜二进制、不猜内容质量。否掉：在后端嗅探文件类型或乱码比例——规则会漂，误杀正常笔记。代价：类型判断依赖前端：文件按后缀、粘贴由用户自选、accept 挡非文本；绕过前端仍可能把任意字符串写进库，P1 接受。

03

粘贴不去重，data_uri 用 uuid urn

选择：只有 URL 入库查重；同一段正文粘两次 = 两条 Resource，各自生成 urn:kc:paste:<uuid>，source 为 null。否掉：按正文哈希去重——会让“同一段话故意存两次”失败，也把去重语义绑到内容上。代价：重复粘贴会多出行，需要用户自己去资源页清理；data_uri 的展示语义留给 FR-11。

拒绝的时点：所有“无效输入”都发生在 createResource 之前。对内容而言只有两种：E_BAD_JSON（body 解析失败或顶层不是对象）与 E_EMPTY_CONTENT（content 空白）。E_BAD_CONTENT_TYPE 是协议形状错误，E_AMBIGUOUS_INPUT 是二选一错误，它们同样在建行前返回 400，但不是“内容质量”判断。建行之后的失败统一变成一条 failed 行 + 422。
  • commit 夹带：看到 a8a18d8 里的 pipelines.ts / qwenembed.ts / 删除 orchestration，不要当成 1.3 的交付；那是 1.2 build3 的重构被一起提交了。页面里用 1.2 b3 标出。
  • “跳过 fetch”是跳过网络：代码仍跑 PassthroughFetcher；这样 stage 顺序、ctx 形状、后续解析都不用为粘贴写特例。
  • 空白检查 trim，但存原串：路由用 trim() 判空，写进 ctx.data.content 的却是原始字符串；前导/尾随空白会保留，偏移也按原串计算。
  • 非字符串 content 的去向：content: 123 不会被当成空白串，而是“没有 content”，最终 E_AMBIGUOUS_INPUT；顶层数组也会走这个码，不是 E_BAD_JSON。
  • url 与 content 同时给：不是“URL 优先”，而是 400 E_AMBIGUOUS_INPUT；前端两种模式互斥，正常不会撞上。
  • 去重不对称：URL 有 findActiveBySource；content 没有。别把“同 URL 拒绝”误推广成“同内容拒绝”。
  • warning 对粘贴通常不出现：thinPage 比较 raw 与 parsed.text；粘贴时两者基本相同，不会触发“可能抓不全”。201 带 warning 主要是 URL 入库的事。
  • Markdown 结构由 chunker 保护：不是 TextParser 解析出来的；改分块器时才会影响代码块/表格是否被切断。
