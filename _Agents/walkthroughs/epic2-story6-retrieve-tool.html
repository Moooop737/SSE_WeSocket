Story 2.6：把检索交给模型

TL;DR

一句话结论与 story 边界

2.6 把“先检索、再把结果塞进 prompt”改成了“模型自己调用检索工具”。它练的是 AI SDK 的 tool calling，不是 Agent loop。

01

工具化

buildRetrieveTool 把 Retriever.search 包成 retrieve 工具；ChatService 在构造期把工具表交给 streamText。

02

有界重查

03

错误走 output

检索判 E_DIMENSION_MISMATCH 时，/chat 仍是 200；错误以 { error: { code, message } } 放进 tool-retrieve 的 output，由模型带着原因收场。

一句话：2.6 只做“把 retrieve 变成模型可调用的工具，并让回答依据工具返回的 Chunk”；历史、引用渲染、观测、DI 都是别的格子或同日附带的一刀。

GLOSSARY

小白词典：tool calling 与 step

这页只需要八个词；每个都配一句大白话。

tool calling
把一张“函数名片”交给模型。模型不执行代码，只输出“我要调用它、参数是什么”；SDK 负责执行，再把结果喂回模型。
tool
四件套：名字、description、inputSchema、execute。名字决定前端看到的 part 类型 tool-名字。
step
一次模型调用，包含它发起的工具执行。模型调一次工具、拿到结果再答，就是两步。
stopWhen
循环的刹车。默认只走 1 步；2.6 显式写 stepCountIs(5)，否则工具刚执行完循环就停了。
tool part
UI Message Stream 里表示工具调用的片段，类型是 tool-retrieve。它有 input-streaming / input-available / output-available / output-error 四种 state。
UI Message Stream
AI SDK 给前端的 SSE 协议；一条 assistant 消息由 text part 和 tool part 组成，不是一个纯字符串。
结构化错误
把错误当成正常 output 返回：{ error: { code, message } }。不是 throw，也不是 HTTP 错误体。
SSE 状态码
响应头只发一次。流开始后才发现检索失败，已经无法把 200 改成 409。

21function buildRetrieveTool(Retriever: Retriever): Tool<RetrieveToolInput, RetrieveToolOutput> {
22 return tool({
23 description: "Search the user's knowledge base with hybrid retrieval (vector + BM25). Call it before answering anything about the user's documents.",
24 inputSchema: z.object({
25 prompt: z.string().describe('search input prompt to knowledge base'),
26 topK: z.number().int().gt(3).lt(20).describe('output knowledge rows you need'),
27 }),
28 execute: async (Input: RetrieveToolInput) => {
29 try {
30 const Sink = getLlmtraceBridge()?.createStageSink() ?? undefined
31 return toOutput(await Retriever.search(Input.prompt, { limit: Input.topK, ...(Sink === undefined ? {} : { sink: Sink }) }))
32 } catch (err) {
33 if (err instanceof RetrieverError) {
34 return { hits: [], vectorCount: 0, lexicalCount: 0, error: { code: err.code, message: err.message } }
35 }
36 logError('E_TOOL_RETRIEVE', String(err))
37 throw err
38 }
39 },
40 })
41}

44 return { hits: Result.hits.map(toHit), vectorCount: Result.vectorCount, lexicalCount: Result.lexicalCount, error: null }

01为什么错误不能 throw（核心）2.6

L1–9

SDK 对 tool error 走 errorMode:'json'；而 Error.message 是非枚举属性，JSON 序列化会把它抹掉。本轮用 node 复现：JSON.stringify(new RetrieverError(...)) 只剩 name/code，中文原因消失。

所以错误必须是正常 output，模型才读得到那句原因。

02输入契约2.6

L13–16

prompt 是检索词，topK 是条数。没有第三个字段——尤其没有从 HTTP 透下来的 limit。

03hit 投影：底子与补丁2.3/2.4

L20–33

2.6 的底子是 chunkId/resourceId/docTitle/source/content/score；chunkIndex/startOffset/endOffset/dataUri/similarity/lexicalScore 是 2026-10-20 为前端命中面板与抽屉补的。字段名保留原生驼峰，方便模型和前端共用一份。

04输出契约2.6

L35–40

vectorCount/lexicalCount 是“过阈值后的条数”，判“库里没有”要看它们，不能看 hits.length——后者已被 topK 截过。错误非 null 时约定 hits 为空、两个 count 为 0。

DECISIONS

关键取舍与踩过的坑

这些取舍多数在 spec-2-6 里就有记录；坑则是实物逼出来的。

D2

依赖走闭包，不走 toolsContext

buildRetrieveTool(Retriever) 在构造期把请求级/进程级 Retriever 烧进 execute；工具不查注册表。DI 之后变的只是 registry 的入参形状，execute 体没动。

D3

toolChoice 保持 auto

不强制 required；用 instructions 约束“先调工具”。代价是模型偶尔可能直接答；required 还会在模型没发 tool-call 时抛 ToolChoiceViolationError，把流变成错误帧。

D6

错误 return 成 output，不改 409

检索发生在 SSE 首帧之后，状态码一次性。结构化 error 让模型能读到中文原因；代价是 part 的 state 永远是 output-available，“失败”要靠读 error 字段。

5

stepCountIs(5)，不是 2

2026-10-21 Lynx 拍：允许模型在有界次数内换检索词。5 步 = 4 次工具往返；仍不开 Agent loop，不串联其他工具。

/R

POST /retrieve 一字不改

它仍是单独验检索的口子、/recall 的调试入口，也是 409 的唯一出口。2.6 只改 /chat 的检索路径。

K

topK 归模型，limit 归 /retrieve

/chat 不再收 limit；工具 schema 收 4–19 的 topK。两个旋钮各管一条路，避免“请求限制”和“模型自选条数”互相打架。

坑（按踩到的顺序）

  • 默认单步。ai@7 的 streamText 默认 stopWhen = isStepCount(1)；不显式写 5，工具执行完循环就停。本机 7.0.148 实测仍在 dist/index.js:8868；spec 当时记的是 7.0.141，默认值未变。
  • throw 会抹掉中文原因。SDK 对 tool error 走 JSON 序列化，Error.message 是非枚举属性。本轮实测：JSON.stringify(new RetrieverError(...)) 只剩 name/code；所以工具必须 return 结构化 error。
  • SSE 状态码一次性。createUIMessageStreamResponse 一发出 200 头和首帧，后面检索失败就不能改 409。/chat 的 200 + 工具 error，与 /retrieve 的 409，是同一个错误的两种出口。
  • 业务错误没有 output-error。RetrieverError 被 catch 成正常 output 后，part state 仍是 output-available；前端必须读 Out.error。只有非 RetrieverError 真 throw 时才会出现 output-error。
  • 键名就是 part 名。registry 的 retrieve 被拼成 tool-retrieve；历史上 retrive 改名时前端没跟上，面板整轮显示“未检索”。
  • 注释漂移。app/web/src/api/chat.ts:98 还写着 stopWhen 2，服务端已是 5；2026-10-21 review 抓到过同款不一致，AC 改 5 后注释没改。读注释不能代替读实现。
  • topK 没有默认值。.gt(3).lt(20) 意味着模型省略或给 3/20 会校验失败；这是 deferred-work 里的已知缺口，不是本页修好的。
  • 数字 [n] 只认最后一条 tool part。referencesOf 取 Parts.at(-1) 作为面板与数字名次的来源；8 位 chunkId 前缀走 allHits，仍能打开更早一次重查的块。右栏面板只显示最后一次的命中。
  • 三种“没有”仍靠模型一句话。空库 / 全无 ready / 有库无命中都是 200 答案体，服务端没有按计数分流；这是 2.1 就接受的口径，不是 2.6 引入的。
  • 库在流前不可达仍是 500。DI 删掉 E_DIMENSION_UNKNOWN 后，/chat 在进入工具前如果库不可达，错误会冒到路由 catch；这与“检索错误一律 200”不是同一条路径，已记 deferred。
