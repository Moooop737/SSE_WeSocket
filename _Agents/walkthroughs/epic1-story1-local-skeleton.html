GLOSSARY · 03

小白词典：先把词说人话

第一次出现的术语在这里给定义；后文不再重复解释。

scaffold
脚手架：把项目的最小可运行骨架搭起来，不是装一个现成模板。这个项目是 Greenfield，手动搭 Hono + Vite。
Hono
一个轻量 Web 框架，路由写法接近 app.get('/path', handler)；配 @hono/node-server 跑在 Node 上。
Vite
前端开发服务器 + 构建工具。开发时它把源码即时编译给浏览器，还能把 /api 代理到后端。
127.0.0.1 / bind
回环地址，只有本机能访问。服务“绑”在这个地址上，局域网里的其他机器就连不进来。
middleware
中间件：请求进入路由前先经过的一层函数，可以读请求、写响应头、记日志，再决定要不要继续。
DI / 容器
依赖注入：对象不在内部自己 new 依赖，而由容器按类型创建并塞进构造器。本项目的容器是 tsyringe。
fail-fast
快速失败：配置不对就在启动时退出，不把坏状态拖到第一次请求才爆。
connection pool
连接池：预先维护一组数据库连接，用时借、用完还，避免每次请求都重新握手。
migration
迁移：把数据库结构变更写成按顺序执行的 SQL 文件；dbmate 负责记录哪些已经跑过。
health probe
健康探针：真正去 ping 依赖，返回 ok/degraded；“进程还活着”不等于“依赖可用”。
halfvec / HNSW
halfvec 是半精度向量，省内存；HNSW 是近似最近邻索引，让向量检索不必全表扫描。
BM25 / ParadeDB
BM25 是关键词相关性打分；ParadeDB 在 Postgres 里提供 BM25（pg_search）与向量（pgvector）能力。

01清扫失败不阻断启动

L65–74

cleanUpOnBoot 只做一件事：调用 repo.markInterruptedAsFailed()；清到行就记 I_BOOT_CLEANUP。

01懒连接 + 两个超时

L13–20

new Pool 只是建对象，不会立刻连库；第一次 query 才握手。所以启动不会因为库慢而卡在建池这一步。

connectionTimeoutMillis=3000 管“连不上就快速失败”，query_timeout=5000 管单条 SQL。两者都是 1.1 review 补的；没有它们，库不可达时启动清扫会无限等。

监听器本身是 1.1 review 的 blocker 修复；logError 这个带 trace_id 的 logger 是 3.1 换的。别把整行都算成 3.1。

TRADEOFFS · 10

关键取舍与踩坑

为什么是这副形状、否掉了什么、什么地方会静默失败。按“会咬人”的程度排。

CHOICE 01

Hono + @hono/node-server，不引 starter

项目是 Greenfield，没有现成模板。Hono 的路由和 Web 标准 Request/Response 让后端保持薄；Node 适配器只负责 listen。代价是要自己处理 hostname、端口、优雅退出这些细节。

CHOICE 02

dbmate + 手写 SQL，不上 ORM

P1 要写表达式索引、halfvec cast、BM25 这些定制 SQL；ORM 帮不上还挡路。迁移是纯 SQL 文件，dbmate 只记版本。参数化查询同样安全，原生 SQL 不等于注入风险。

CHOICE 03

健康检查只做探针，不做门

1.1 只实现“告诉你坏没坏”，没有实现“坏了就不让入库”。后者需要路由层统一读 readiness，属于跨 story 的闸门；retro 把它记成 open action item，没有偷偷补上。

CHOICE 04

AI SDK 这格一行没用

Embedder / ChatModel 只是接口占位；真正的 embedMany / streamText 从 Epic 2 才登场。这也是为什么后来两个接口会被 AI SDK 句柄取代。

踩坑清单

  • hostname 不是 host。@hono/node-server 写成 host 会被静默忽略，退回 0.0.0.0。1.1 review 实测确认；安全边界靠这一行。
  • 连接池必须有 error 监听。远程 PG 掐空闲连接时，没有监听器就是未捕获异常，进程静默崩；再加连接/查询超时，库不可达时启动清扫才不会无限等。
  • fail-fast 不可 catch。AppConfig 构造器直接 process.exit(1)；测试只能开子进程看退出码与 stdout，不能在同进程 expect(...).toThrow。
  • degraded 不拦业务。retro E-1 的准确表述是“AC 与实现各说一半”：health 探针工作正常，但入库/问答路由与它零耦合。别把 503 当成闸门。
  • 探针分组不是分级。服务组只按实际依赖归类（postgres / ollama）；没有 critical / advisory 权重，ollama.running 仍是恒 ok:true 的信息项，不参与 503。拆 /ready、按探针独立缓存也仍被否决。
  • 启动清扫只跑一次，失败被吞。数据库短暂不可达时，processing 行会一直卡着；而且清扫与新任务之间没有“哪些算遗留”的下界。deferred-work 已记竞态。
  • 清扫没有真崩溃验证。retro 用优雅停止模拟，在途任务照样跑完；要验真崩溃得 kill -9，本轮被安全策略拦下。代码路径存在，不等于端到端验过。
  • AC 的四个端口文件已经不在。ports/retriever.ts 被检索改造 dda283c 删；repository/embedder/chat-model 被 2026-10-16 重构删。今天按 adapter/contract.ts + retrieve/contracts.ts + agent/tool/contracts.ts 读。
  • 缺 Key 的错误码变了。1.1 是 E_CONFIG_MISSING 点名 DEEPSEEK_API_KEY；DI 之后是 E_CHAT_MODEL（该模型不在册）。现象都是启动即退，但排错时别照着旧错误码找。
  • 别只读第一份迁移。20261010025742 里还是 dim + halfvec(1024)；后续四个迁移才把它改成 dimension、不定长 halfvec、partial HNSW 与 CHECK。看最终形状要连起来读。
  • 前端 Key 边界靠约定 + 构建规则。Vite 只暴露 VITE_ 前缀变量；本页涉及的 Key 都不带这个前缀，app/web 里也 grep 不到。新增配置时别把服务端 Key 改名成 VITE_*。
