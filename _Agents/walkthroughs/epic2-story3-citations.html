01 · 结论与边界

先收口，再划边界

Story 2.3 的交付不是“又一个检索接口”，而是把回答里的标号接到本轮真实命中上。先记住这句话，后面的代码都围绕它。

一句话结论：Story 2.3 把模型写在正文里的 [n] / 8 位 chunkId 前缀，映射到同一条流里 tool-retrieve part 的真实命中；越界或对不上的标号保持纯文本，右栏只列“回答真正引用到”的命中。

同一条流

前端不再平行打 POST /retrieve。命中来自那条 assistant 消息的 tool part，回答与引用天然同源。

越界、对不上、本条没有命中：原样留文字。找不到 chunkId 不是异常，而是“这枚标号不可信”。

03 · 小白词典

先认四个词，再读代码

tool-retrieve 的四种状态是这一页的入口；剩下三个词都围绕“命中身份”转。

part.stateoutput / errorreferencesOf 的说法用户看到
input-streaming / input-available还没有 outputrunning正在检索…（不是“没查到”）
output-availableerror: null，且 hits 是数组ready引用面板 / 命中行
output-availableerror 非空failed本次检索失败 · 后端文案
output-error工具自己抛了错failed本次检索失败 · errorText
output-available形状不对（hits 不是数组）failed检索结果形状不符合契约
tool part
UIMessage 的 parts 里的一段，带 type、state、output。这里只关心 tool-retrieve。
chunkId
数据库里 chunk 的 UUID。引用、去重、高亮都按它认人；数组下标会随重查换位置，不能当身份。
[n]
1–2 位名次，读作“最后一次检索的第 n 条”。早期回答/兜底会出现；当前提示词更偏好 8 位 id。模型可能写错，界面不替它背书。
8 位 id
模型实测会写 chunkId 前 8 位。先在本条 allHits 里找；本轮完全没检索时才往历史找。
allHits
同一条 assistant 消息里所有成功 retrieve part 的命中，按 chunkId 去重；只给 8 位 id 解析用。
cited
正文真正点到、且能解析的命中，按首次出现排序。右栏列的就是这一批，不是工具的整份输出。

01MARKER 与 hitFor：两种写法，越界返回 null

L177–194

07 · 取舍与坑

为什么是这副形状

这一节记录“当时否掉了什么”和“以后改哪里会静默坏掉”。

D1

唯一真相 = 同一条流

2026-10-20 之前 /ask 平行打一次 /retrieve，两批命中并排放着却不互相担保。现在回答与命中来自同一次工具调用；/recall 仍打 /retrieve，因为它是“只检索不生成”的调试台。

D2

[n] 是模型写的，不是界面的声明

界面只做“顺序对齐”：第 n 个标号对应最后一次 hits 的第 n 条。对不上就留文字，不替模型编来源，也不给假按钮。

D3

1..N 按首次出现，不按召回名次

Lynx 2026-10-20 定：正文出现 2、3、6、8 的跳号很难读。右栏、按钮、正文统一读 citedHits 的首次出现顺序。

D4

多步：面板最后一次，解析用全集

hits 给面板和数字名次；allHits 给 8 位 chunkId。数字名次跨 part 没有意义，跨轮也没有意义；8 位 id 全局唯一，才能跨。

D5

来源删除：快照可看 + 标注

2026-10-21 Lynx 拍板，原 AC 的“不可点击 / 410”作废。抽屉按 resourceId 查一次，404 才标“来源已删除”；内容仍来自回答时的快照。

D6

越界不是异常，是“不可信标号”

hitFor 返回 null，withCitations 原样输出，citedHits 不收录。整页不因模型写了一个 [99] 落错误边界。

旧 AC 不要写反：“来源删除后不可点击 / 410”已经作废。现在的口径是快照仍可看，只在抽屉/引用处标注“来源已删除”；这条落地在 2.4，不是 2.3 的按钮逻辑。
  • 坑 1 · 工具键名。后端 registry 的键名就是 part 名。2026-10-20 从 retrive 改成 retrieve，前端没跟，面板显示“未检索”但模型其实查了 10 条。改键名要连 RETRIEVE_TOOL 一起改。
  • 坑 2 · 缺 chunkId 的畸形 hit。hitFor 的 byId 仍直接读 H.chunkId.toLowerCase()；旧载荷/字段漂移让某条 hit 缺字段时，仍可能抛。这与“越界索引”不是同一件事，已记在 deferred-work（2026-10-21），本轮没有修。
  • 坑 3 · 数字名次只属于本条。同一个 [1] 在上一轮指的是另一条命中；往历史里解就是串台。跨轮只服务 8 位 id。
  • 坑 4 · 8 位全是数字。[12345678] 仍按 chunkId 前缀解析，不能因为“看起来像数字”就当名次查下标。
  • 坑 5 · 只取最后一条 tool part。面板显示最新战果；更早一次重查的命中只能通过 8 位 id 被正文引用，数字名次对不上是预期行为，不是 bug。
  • 坑 6 · 来源删除只认 404。500/网络失败时 goneHitId 保持 null，不把“未知”说成“已删除”；快照仍渲染。
  • 坑 7 · 链接清洗不能吃掉标号。plain() 把 [3](地址) 的 URL 去掉、标号留下；否则点 [n] 定位就断了。
