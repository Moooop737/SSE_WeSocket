01 · 结论与边界

断言是硬门，judge 给分数，人保留改分权

7.4 不把「评回答」做成一条黑箱总分；证据分层摆开，结论按拍板规则合成。

01 / ASSERT

expect / reject 断言

每条 case 两组断言：必须出现、必须不出现。默认子串大小写不敏感，单条可开正则；保存时校验正则可编译。全部满足才算过。

02 / JUDGE

三维分 + case verdict

rubric v1 让 judge 给 groundedness / correctness / citation（0–2）和 pass/fail。没有默认模型、不强制不同源；单条失败只记该 case。

03 / HUMAN

人可以改分或独立打分

人判单独存 human_results，机器结果不覆盖；一致率用「人判 vs judge 原值」算。还可以修正错误的题面，写回题集、不动历史快照。

04 / VERDICT

断言硬门 + 取更严

断言失败直接 fail；judge 与人判都在时两者都 pass 才 pass；只有一个就听它；都没有且有断言 → pass，没断言 → unscored。

不属于 7.4：多次采样与置信区间（未排期）、pairwise（后续）、人工标注平台（不做）、gold 的前端挑选/编辑（未排期）、把 judge 分数与检索指标加权成一条总分（不做）；浏览器视觉归 Lynx。

02 · 一次答案评测怎么走

模式从快照来，结论在读取时合

运行期只写机器证据；人判之后，详情与聚合用同一套规则重算最终判定。

1 · 模式

  • judge_model非空 → answer
  • case 断言任一 → answer
  • 否则retrieval

2 · 运行

  • 回答generateText + tools
  • 断言expect / reject
  • judgeOutput.object
  • 机器 verdict写入 results

3 · 人判后

  • 人判human_results
  • 最终finalVerdict
  • 聚合summarizeAnswerResults
  • 一致率按 level
为什么读时重算：机器 verdict 是运行时的快照；人判是之后才进来的。把「断言 > 人判 > judge」放在一个纯函数里，列表、详情、对照都调它，就不会出现两套口径。

06 · 取舍与坑

为什么不合成一条总分

断言、judge、人判是三种证据，不是三个可以随意加权的分数。

WHY LAYERS

证据分层，判定只取更严

断言是硬门；judge 与人判都在时两者都 pass 才 pass。没有权重表，也没有「机器 0.7 + 人 0.3」这种拍脑袋的数；要调整只改 rubric 的 pass 标准。

NO OVERWRITE

人判不改机器分

一致率需要机器原值；人判单独存。页面上人判是最终依据，但机器分仍可回看——这样既能纠错，也能知道机器错在哪。

ANSWER PATH

复用指令与工具，不复用 ChatService

ChatService 绑死历史、SSE 与落库；评测要的是无会话的 generateText。复用边界画在「INSTRUCTIONS + tools」，改动面最小。

NO COLUMN

模式用快照推断

加 kind 列会让旧 run 回填、接口多一字段；judge 或断言本身就在快照里，推导即可。代价是每次读要多扫一遍 cases，规模小可接受。

ERROR ≠ SCORE

回答错与 judge 错分开

回答失败是 case 失败；judge 失败是基础设施失败，断言能兜就兜，兜不住就 unscored，不假装 0 分。

CROSS MODE

跨模式不硬比

检索 run 的 recall 与答案 run 的 judge 分不是同一量纲；基线模式不同时只提示，不造一张看似可比的表。

踩坑：人判保存后必须重拉详情，否则 final_verdict/一致率还是旧的；judge 的片段要截断，否则长块会把 prompt 撑爆；summarizeResults 不能拿来算答案 run（它把 recall≤0 当 failed）。
