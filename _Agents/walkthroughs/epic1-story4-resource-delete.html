01

软删留痕

resources.deleted_at 打时间戳，行还在；历史引用、审计和排障都还能看到「它曾经存在」。同一事务里把 chunks 物理删掉。

02

取消归服务端

pg 写入不吃 signal。取消若落在 INSERT/UPDATE 之间，事务会提交成 ready；写完后必须再查一次 Signal.aborted，把那一笔撤回。

MAP · 02

全局地图：四条链路各管一段

删除不是一条 SQL，而是「请求 → 取消 → 写入守卫 → 软删事务 → 检索过滤」五段接力。

① 删除请求链

  • 形状校验uuidOk → 400 E_BAD_ID
  • 读活跃行getResource（过滤 deleted_at）
  • 处理中先取消inflight.abort(id)
  • 软删事务UPDATE resources + DELETE chunks
  • 响应204 / 404 / 500

② 取消请求链

  • 校验 + 读行404 / 409 E_NOT_PROCESSING
  • 按登记inflight.abort(id) → boolean
  • 按不下去409 E_NOT_INFLIGHT + 重读状态
  • 按下去202（异步生效）
  • 行稍后failed / 入库取消

③ 写入守卫链

  • 事务内读资源行AND deleted_at IS NULL
  • 写 chunks + embeddings同事务
  • 转 readyrowCount=0 → E_RESOURCE_GONE
  • 写后复查Signal.aborted → 撤回
  • 登记注销finally remove(id, ctrl)

④ 防孤儿数据链

  • chunks.resource_idFK → resources ON DELETE CASCADE
  • embeddings.source_idFK → chunks ON DELETE CASCADE
  • 软删事务DELETE chunks 带走向量
  • 检索 SQLJOIN resources ... deleted_at IS NULL
  • 全库核对orphan vectors = 0

GLOSSARY · 03

小白词典：这一页会反复出现的词

不追求教科书定义，只求读代码时不再卡住。

软删（soft delete）
不删行，只把 deleted_at 写成当前时间。所有正常查询都带 deleted_at IS NULL，行就「看不见但还在」。
物理删（hard delete）
真的 DELETE FROM。chunks 用物理删，因为它要立刻从 BM25/HNSW 索引里消失。
FK CASCADE
外键上的「父行删了，子行自动跟着删」。embeddings.source_id → chunks.id 就是这条规则，所以删 chunks 不用手写删向量。
AbortController
取消开关。调用 ctrl.abort() 后，ctrl.signal.aborted 变 true；fetch/embed 这类长操作收到 signal 会抛中断错。
进程级 Map
只活在当前 Node 进程里的表。Map<resourceId, AbortController> 让「按取消」的路由找到「跑任务」的那只开关。
事务（transaction）
一组 SQL 要么全成功、要么全回滚。写入 chunks、向量、转 ready 必须同事务，否则会出现「有向量没 chunk」这种半截数据。
写守卫
在写库前/写库后再查一次条件（资源是否已删、是否已取消）。它补的是「signal 管不到 pg 调用」这段盲区。
202 / 204
202 = 请求已接受、异步生效（abort 按下，行稍后才转 failed）；204 = 成功且没有响应体（软删完成）。

06POST /:id/abort：只取消，不删除

L83–99

三层判定：读不到 → 404；状态不是 processing → 409 E_NOT_PROCESSING；登记里没有 → 重读一次状态，回 409 E_NOT_INFLIGHT，不再猜「服务可能重启过」。

L196

01文件头就是契约

L1–8

持有者是管线：建行之后 add，结束时在 finally 里 remove。登记只在内存，进程重启即空，遗留 processing 行交给启动清扫。

abort() 只回答「此前有登记、且现在按下了」，不校验资源状态、不碰数据库——那是调用方的事。这一分工让路由可以在读库之后、软删之前安全地按一下。

02add / remove：remove 必须比对 controller

L19–25

remove(Id, Ctrl) 先比对 this.inflight.get(Id) === Ctrl 再删。若同一个 id 被重新入库复用，旧 run 的迟到 finally 不该把新任务的登记摘掉（review A5，ec36c9e 修复）。

代价是调用方必须把 controller 一起传进来；只传 id 的旧签名已经不存在。

03abort：按下并回答 boolean

TRADEOFFS · 07

关键取舍与踩过的坑

这一节回答「为什么不是另一种写法」，以及哪些坑是实测出来的、不是推演出来的。

01

软删 resources + 物理删 chunks

资源行要留痕（历史引用、审计、排障），所以只写 deleted_at；检索数据要立刻消失，所以 chunks 真删。两者放同一事务，避免「列表里没了但还搜得到」或「搜不到了但列表还在」。

否掉了：整行硬删（历史引用失去锚点）、chunks 也软删（BM25/HNSW 索引里仍留数据，检索必须再加一层过滤，且索引会膨胀）。

02

取消开关归服务端，不归 HTTP 连接

管线自己 new AbortController()，按 resourceId 登记。任意请求都能按，客户端断连不再是否决票。

为什么：客户端断连就取消，会让「批量上传后关页面」变成灾难；防泄漏改由三条服务端腿保证：inflight.abort、fetch/embed 各自的 30s 超时、启动清扫。

03

/abort 只取消不删除

取消是「停止任务」，删除是「移除资源」，两个意图分开。abort 成功回 202，行稍后转 failed(入库取消) 但仍在列表里；用户想清掉再按 DELETE。

否掉了：abort 顺手软删（会让「取消」变成不可逆的破坏性动作，也混淆两个 AC）。

04

DELETE 遇 processing 先 abort 再软删

顺序反了会给已删资源补写一批 chunks。先按取消把窗口缩到最小，再进软删事务；软删事务里的 deleted_at 谓词负责兜住残余竞态。

按不下去怎么办：（重启遗留/异进程）当前代码用 updateResourceStatus(id, 'failed', '入库中断') 自己收口，避免留下永远 processing 的行。

  • 真实坑 C1：取消落在写入期，事务已提交成 ready。写入不是可中断的：pg 调用不吃 signal，写入前最后一次检查之后，取消仍可能落下。修复是写完再查 Signal.aborted，走 cancelled() 撤回。复现序列：processing/chunks=0 → ready/chunks=16 → ready/chunks=0 → failed/chunks=0/入库取消。中间那帧 ready 就是 bug 本身——202 承诺了「不会转为已就绪」，但只 abort 不删除时 deleted_at 仍为 NULL，写守卫谓词通过，事务照常提交。
  • 死锁断言被 200 轮实测否证，不是「没遇到」。review 原推理：写入方 INSERT chunks → UPDATE resources，软删方 UPDATE resources → DELETE chunks，锁顺序相反 ⇒ 环等待。实测漏了一步：INSERT INTO chunks 会因外键先对父 resources 行加 KEY SHARE 锁，父行成为唯一排队点；两个方向都只有一把锁要排，环闭合不了。两个顺序各 100 轮（共 200 轮），40P01 死锁 0 次、57014 超时 0 次。
  • 真正换名字的残余风险：DELETE 会等整个写入事务。场景一证明 DELETE 会阻塞到写入 COMMIT。16 块 <1ms 无感；等到几千块、INSERT 参数逼近 65535，写入事务可达数秒，DELETE 会撞 query_timeout: 5000 报 500 E_DELETE。用户看到「删除失败」，但 abort 其实已按下、行随后照样转 failed——取消成功了，删除没有。归口在「写入分批」，不是本轮的锁问题。
  • 写守卫只救「删除 + 写入」，救不了「只取消不删除」。AND deleted_at IS NULL 的前提是有人写 deleted_at；/abort 不写。别看到守卫就以为取消路径也安全——这是 C1 存在的根因，也是 review 反向收获。
  • 登记只在内存，跨进程/重启即失效。第二个进程或重启后 /abort 诚实回 409 E_NOT_INFLIGHT；最终收口靠启动清扫或 DELETE 的「入库中断」分支。Redis 存不了 AbortController（进程内活对象，序列化即失效），跨进程只能传「取消意图」，所以本地 Map 无论如何都在。
  • 取消延迟有下限：同步 parse/chunk 是地板。parser 与 chunker 是同步的，这段时间事件循环被占，连 DELETE/abort 请求本身都进不来；只能在异步边界观测取消，最坏要等当前同步段或写事务跑完。
