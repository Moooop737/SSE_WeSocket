01 · 结论与边界

这一格只做连接，不做评测业务

7.0 的成果不是“评测功能”，而是一条可以复用的库选择：评测世界与主世界同构，差别只在 pgpool。题集、运行、对照、答案评测从 7.1 才开始。

01 / SHARED

默认共享主库

不配 EVAL_DATABASE_URL 时，EvalAssembly 直接把主库的 PostgresRepo 与 RetrieverHandle 交给评测路由。零配置、同一份语料；评测产生的资源/痕迹会出现在主库里，按 /eval 前缀识别。

02 / ISOLATED

可选隔离库

配了 URL 就构造第二个 pgpool 连 ragdb_eval，再用同一批服务类组装第二套 Repo/Retriever。主库的检索、列表、聊天统计不受影响；代价是要建库、灌语料。

03 / ONE SHAPE

同构装配，换 pool

两种模式复用同一批类；ObjectStore、Embedding、RetrieverFactory、InflightRegistry 共享。不改 Repo 为多实例容器，也不提前做 namespace。

04 / OBSERVE

trace、health、徽标

评测路由由自己的 trace 壳记一次，route 带 /eval；/health 多一个 eval 服务组；三个评测页页头显示共享主库 / 隔离库 / 检测中 / 未知。

不配 URL：零成本，共用主库

同一只 pgpool、同一份 resources/chunks/embeddings；评测的资源操作会真实落到主库。适合“先跑起来”和“就评生产语料”。健康探针标 mode=shared，不重复 ping。

03 · 小白词典

读代码前先对齐几个词

这些词在后面的块里反复出现；先按“人话”记住，再看实现。

pgpool
PostgreSQL 连接池。主库与评测库各有一只，互不共享；共享模式只有主库那只。
装配（assembly）
把配置、连接、Repo、服务按依赖关系拼起来的那一步。EvalAssembly 只负责“评测用哪套”。
同构
同一批类、同一套迁移、同一套行为；差别只在注入的 Repo/池。不是第二套业务代码。
route 模板
trace 里记的路由形状，例如 POST /eval/retrieve。Hono 的 matchedRoutes 会带子应用的完整前缀。
ingest 链
storage fetch → parse → chunk → embed → write。隔离 seed 不另写一套，还是走这条链。
内容寻址 key
评测对象的 MinIO key 用 eval/<sha256>/<原 key>，同一内容可重跑，主库对象被删也不影响评测。
幂等 seed
按 content_hash 查评测库：ready 跳过、软删恢复、其余状态重试；重复跑不重复建行。
健康探针
/health 的叶子检查；全部通过才是 200 ok，否则 degraded / 503。eval 组是这一层新增的。

11 · 取舍与踩坑

为什么是这些形状

每一条都能在上面的代码里找到落点；这里讲被否掉的方案和容易踩的坑。

DECISION 01

默认共享，不把缺 URL 当“不可用”

最初的 AC 写成“缺失时评测整体不可用”，Lynx 当天纠偏：评测默认就该跑主库，缺 URL 是共享模式，不是关闭功能。于是 status 返回 mode，前端也不做禁用门。

DECISION 02

评测世界 = 主世界换 pgpool

不复制一套业务代码，也不把 Repo 改成多实例容器。shared 复用主库的 repo/handle；isolated 只多一个池和一套绑定它的服务。两边的迁移、检索、ingest 都是同一套。

DECISION 03

不改 endpoint.ts，用注册顺序隔开

Hono 的 use(*) 只作用于其后注册的路由：入口先挂 /eval，子应用内 status 先注册。代价是位置约束——把 app.route(/eval) 挪到主壳下面，双层 trace 就会回来。文件头和 index 注释都留了提示。

DECISION 04

不加 origin 列，route 前缀就是标记

评测路由天然带 /eval，Hono 子应用的 matchedRoutes 也返回全前缀；GET /traces 已支持按 route 过滤。trace 行里的 resource_id/session_id 只在选中的库里可解释，放主库反而会悬空。

DECISION 05

seed 复制对象，不共享主库 key

评测对象住 eval/<sha256>/<原 key>。主库 purge 自己的对象不会把评测的原始件带走；同一内容可重跑，不同内容不撞 data_uri。代价是 MinIO 多一份字节。

DECISION 06

health 的 eval 组：全绿口径不破例

shared 恒 ok；isolated 真 ping。隔离库不可达会让 /health degraded/503——这是显式取舍：健康页要能看见评测库坏了。若只想摆事实，把 ok 改成 true、detail 写 reachable=false。

DECISION 07

前端只取一次，不做轮询

mode 由启动期 env 决定，运行中不会变；进入页面取一次 /eval/status 足够。代价是后端重启切模式后要刷新页面。未知态用红点，不把缺省画成绿。

  • 本地 .env 已有 EVAL_DATABASE_URL：当前工作区默认是隔离模式，不是共享。要验共享必须显式 EVAL_DATABASE_URL= 起服务；测试里 eval-route.test.ts 也主动删了这个 env。
  • EvalPostgresRepo 不能提前注入：如果把 container.resolve(EvalPostgresRepo) 放进构造器依赖，shared 模式也会建第二个池，甚至在无 URL 时抛错。必须像 assembly 这样懒解析。
  • Hono 注册顺序是位置约束：入口里 app.route(/eval) 必须早于主壳；子应用里 /status 必须早于 trace 壳。任何一次重排都会让双层 trace 或 status 落 trace 回来。
  • seed 的块对齐依赖同一 bytes/parser/chunker：45/45 篇块内容一致是实测结果，不是自动保证。某篇若用了非默认 chunker，gold 的 chunk_index 会对不上；那时要么按主库原样复制该篇，要么重新出题。
  • CREATE DATABASE 有 SQL 边界：不能进事务、不能参数化；库名必须白名单校验后加双引号。连接串只进子进程 env，不进 argv。
  • endpoint.ts 的 /resources 跳过是既有代码（已在 136857e 提交）：与 3.4 的 ingest trace 口径冲突，但不属于 7.0；本格只加 /eval 的注册顺序，没有动它。去留由 Lynx 定。
  • 7.0 的新文件还在未提交面：136857e 里能看到的是 eval-probe / eval-cases 与 Epic 5 尾巴；本页的 eval-db / EvalAssembly / /eval 路由 / setup / seed 是当前工作区的新增，边界按代码而非提交号划。
  • 共享模式的评测痕迹会进主库：这是共享的代价，不是 bug；按 route 前缀过滤即可。要彻底不混，就切隔离模式。
  • health 的 detail 是字符串数组：前端 detailList 只认字符串/数组；给对象会渲染空，给数组才能变成 Tag。
