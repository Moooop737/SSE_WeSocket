01 · 结论与边界

这一格交付什么，不交付什么

5.1 的成果不是“文件上传页面”，而是一层可被 5.2/5.3/5.4 复用的对象存储能力，加上启动与健康检查。

01 / CONTRACT

对象存储形状

put / stat / get / delete / presignGet / presignPut / ping / ensureBucket。对象不存在返回 null，其它失败统一 ObjectStoreError。

02 / WIRING

装配与启动

ObjectStoreHandle 只经 adapter/contract.ts 交出；启动时 ensureBucket() 失败只告警；/health 多一张 s3 卡。

03 / EVIDENCE

真跑过的东西

真 MinIO roundtrip、Range 206、过期 403、Host 不一致 403、presignPut 正确类型 200 / 错类型 403、建桶幂等。

不属于 5.1：resources.storage_* 列、ingest 的 store 段、GET /resources/:id/original 302、上传路由、ZIP 解析、公网登录/退出吊销/一次性 token（P5）。前端 health 页的等高布局是 Lynx 的邻接改动，不在本格 AC。

14 · 取舍与踩坑

为什么这么写，否掉了什么

这几条如果忘了，下一次很容易写回错误版本。

A

Host 必须一致

SigV4 把 Host 签进 URL。后端用域名签、浏览器用 IP 请求会 SignatureDoesNotMatch。所以 S3_ENDPOINT 必须是浏览器实际访问的那个 Host；公网反代要保留 Host。

B

contentType 可选，但给了就签

presignPut 默认只签 host；传了 contentType 就用 signableHeaders 显式签 content-type。body 不在签名里，上传后必须 HEAD 校验内容。

C

MinIO 的 checksum 兼容

SDK 默认可能附加 CRC 校验和；这里设 WHEN_REQUIRED，避免 S3 兼容服务不认。代价是默认不做响应校验，生产要按需打开。

D

404 的两种含义

对象 404 → 返回 null；桶 404 → 抛 ObjectStoreError。不要把“桶没建好”伪装成“对象不存在”，否则调用方会把基础设施故障当业务空值。

health 拍板 A：保持“全绿才 200”，storage 是第三个关键服务；MinIO 挂了整体 503。boot 仍 non-blocking，两者语义不同但都明确。
Review 发现的上公网前事项：当前应用使用 MinIO root 凭据；5.2 要换专用用户（含 s3:ListBucket 以支持 HeadBucket），生产预建桶、不给 CreateBucket。已记入 deferred。
验证债：test/ 被 gitignore，health 测试与 env loader 修复不在版本控制；新 storage/config 测试在 src/ 下，但仍依赖 test/setup-env.ts。这是已知跨阶段项。
