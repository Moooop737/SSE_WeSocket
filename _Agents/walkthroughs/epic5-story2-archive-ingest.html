01 · 结论与边界

这一格交付什么，不交付什么

5.2 的成果是资源生命周期的骨架：六状态、data_uri、两段式上传、从 MinIO 读的 ingest、302 下载、软删恢复。5.3 在它上面加内容身份、批量顺序、回收站与重入库；5.4 另开代码库域。

01 / ARCHIVE

原始字节先落地

文件：presign PUT 由浏览器直传；URL：服务端抓取后写入；粘贴：直接写 UTF-8 文本。三者都变成一条资源行 + 一个 MinIO 对象。

02 / INGEST

ingest 只认 data_uri

ingest 不再抓 URL：storage fetcher 从 MinIO 读回字节，parse/chunk/embed/write 五段口径与 3.4 一致。

03 / READ

下载与恢复

下载 302 到 1h presigned GET（attachment + no-store）；软删只写 deleted_at、保留对象；restore 先 stat 再回落 uploaded，不自动 ingest。

不属于 5.2：SHA-256 去重与两段式批量（5.3）、回收站列表/彻底删除（5.3）、ready/失败重入库（5.3）、代码库 ZIP（5.4）、multipart、PDF/Word、后台任务队列。

02 · 全局地图

一条资源行，两次写盘

归档只负责原始内容；解析、切块、向量全部推迟到 ingest。任何一步失败都落状态与 error_reason，不假装成功。

三条归档路径

  • 文件create → presign PUT → uploading
  • URLfetch → put → uploaded
  • 粘贴put → uploaded

ingest 五段

  • fetchMinIO 读回 data_uri
  • parse / chunk正文与分块
  • embed / write向量与事务写入

读与恢复

  • 下载302 presigned GET
  • 软删deleted_at，对象保留
  • 恢复stat → uploaded

六状态：uploading / uploaded / processing / ready / upload_failed / process_failed。前两态属于归档，中间属于 ingest，最后两态是失败留痕；重试语义由 5.3 补齐。

03 · 小白词典

读代码前先对齐六个词

data_uri
内部归档地址，形如 kc://oss/minio/kbfile/<key>；source 只记外部 URL，两者不混。
presign PUT
后端签一个带时效的上传地址，浏览器把文件字节直接 PUT 给 MinIO，后端不代理文件内容。
stat
向对象存储问对象在不在、多大、什么类型；不是下载内容。归档后由 ingest 做这个确认。
五段管线
fetch → parse → chunk → embed → write。3.4 定的口径；5.2 只把 fetch 的来源换成 MinIO。
302
后端不转发文件，只回一个跳转目标；浏览器随后直连 MinIO 的 presigned URL。
软删
只写 deleted_at 并移除 chunks/embeddings，MinIO 原对象保留，供恢复或后续彻底删除。

10 · 取舍与踩坑

为什么是这些形状

DECISION 01

文件直传，URL/粘贴后端写

文件最大 10 MiB，直传省后端带宽；URL/粘贴本来就要在服务端处理，顺手写入。三条路径最终都落成同一种 data_uri。

DECISION 02

ingest 不抓 URL

网页会变，抓取时刻的字节才是一份稳定语料。5.2 把 fetch 从“网络”换成“对象存储”，五段管线的其余四段完全不动。

DECISION 03

下载走 302

后端不代理文件字节；presigned GET 让浏览器直连 MinIO。代价是 URL 本身是临时凭证，日志与 trace 都不能记。

DECISION 04

软删保留对象

删除只清检索数据与 deleted_at；恢复因此不需要重新上传。真正释放对象与 hash 是 5.3 的彻底删除。

  • PUT 失败会留下 uploading 行：浏览器直传失败时后端不知道，行会停到 24h 启动清扫；这是已知缺口，记在 deferred。
  • HTTPS 页面直传 HTTP MinIO 会被 mixed content 拦：CORS 已实测默认放行；手测用 http://localhost:5173 规避，TLS 属部署项。
  • 旧 data_uri 不回填：不是 kc:// 的行在 ingest/download/restore 统一 E_NO_ORIGINAL；旧数据已清空。
  • 归档 trace 是 0 段：观测只写在 POST /resources/:id/ingest 的五段；归档的 trace 只回填 resource_id。
