一句话区分：SSE 是传输层（HTTP 分块 + data: 事件）；UI Message Stream 是应用层协议（每帧 JSON 的 type 定义 start/text-delta/tool/error/finish）。它不是「一个 JSON 对象分几次写」，而是「一串各自独立的 JSON 事件」。
GLOSSARY

小白词典

先把这 9 个词说清楚，后面的代码就不猜了。

SSE
Server-Sent Events。HTTP 响应不结束，服务端持续写 data: ... 行；浏览器按事件接收。适合单向推送。
frame（帧）
SSE 里的一次事件：一行或多行 data:，以空行结束。本页每条 data: 是一个 JSON chunk。
UI Message Stream
AI SDK 定义的应用层协议。chunk 的 type 有 start、text-delta、tool-input-available、error、abort、finish 等；useChat 按这些语义更新消息。
UIMessage / parts
前端的一条消息不是 text: string，而是 { role, parts: [...] }。text、reasoning、tool-retrieve、data part 都住在这个数组里。
text-delta
一段增量文字。多个 delta 追加到同一个 text part；ChatThread 每来一帧就多渲染几个字，这就是「逐字」。
tool part
tool-retrieve 这类 part 记录模型调用工具的四态：input-streaming / input-available / output-available / output-error。它是 2.6 的交付，不是 2.2 的 data part。
data part / transient
data-* 是自定义数据 part。transient: true 表示只实时通知，不写进 message.parts，所以不会进历史、刷新后消失。
submitted / streaming / ready / error
useChat 的四态：请求已发、首块未到 / 正在收块 / 正常结束或已取消 / 失败。Loading 看前两态。
error 帧 vs abort 帧
{"type":"error","errorText":"..."} 会让 useChat().error 有值；{"type":"abort"} 只是中止标记，客户端不一定会报错——这是本页要讲清的关键差别。

DECISIONS

关键取舍与踩坑

为什么用 UI Message Stream、为什么选「取消前一条」、为什么 abort 帧不能当 error 用。

01

用 UI Message Stream，而不是自定义 JSON

useChat、UIMessage.parts、tool part、error/abort 语义都是 SDK 现成的；自己发明协议要重写解析、状态与工具序列化。代价是协议帧多、必须按 type 理解，不能当普通 JSON 读。

02

忙时取消前一条，而不是排队/拒绝

AC 三选一，选了「取消」：先 stop() 再发。代价是 stop() 没有上界，所以加 800ms 竞速；停不干净就拒绝这一问并提示，绝不让两条流互相拨 status。

03

错误文案固定「问答失败」

流内 onError 只回一句固定话，详细错误进服务端日志。好处是不把 provider 的原始错误/密钥片段泄给浏览器；代价是用户拿不到可操作的细节，排障要看服务端。

04

中断不落 assistant

取消/中断直接 return，库里只留 user 消息。好处是历史里不会出现半截答案被当结论；代价是刷新后半截消失，前端「未完整」标记只在内存。

05

命中用 tool part，不用 transient data part

2.6 把命中放进 tool-retrieve output，成为 assistant 消息的一部分，可持久化、可在历史里回看；transient data part 只适合实时进度，不适合引用。原 sources data part 方案因此退役。

06

超时三条款整体推后

Lynx 2026-10-15 定「先把 SDK 跑通」；没有真实上游首块延迟样本前，拍一个超时值只是拍脑袋。代价是 inter-token 卡住时不会自动标未完整，只能手动停。

容易踩的 8 个坑

  • 把 commit 标题当边界。dda283c 叫 story 2-2 dev1，内容是 2.1 的检索/路由；b9ad65e 叫 build 3，才是 2.2 的前端接线。看 diff，不看标题。
  • 以为 error 帧能改 HTTP 状态。Response 返回时 200 已经发出；模型中途报错只能发 {"type":"error"}，前端从 useChat().error 读，路由的 500 覆盖不到。
  • 把 abort 帧当 error。本机实验：只喂 {"type":"abort"}，Chat 最终 status 是 ready、error 为 none，半截 text part 甚至还是 state:"streaming"。所以手动停止必须自己 markCut。
  • 在 submitted 阶段给上一轮挂光标。submitted 时本轮 assistant 还没进 messages；按「最后一条 assistant」挂光标会挂到上一轮写完的回答上。代码用 status === 'streaming' 挡住。
  • 错误时无脑标半截。非 2xx 发生在 assistant 出现之前；必须判 messages.at(-1)?.role === 'assistant'，否则会把上一轮完整回答永久标成未完整（cut 从不回收）。
  • 混淆两个 onError。streamText 的 onError 只记日志/给 trace；toUIMessageStream 的 onError 才决定客户端 errorText。改错一个，用户看到的文案不会变。
  • 以为 stop() 有上界。它没有；所以 800ms 竞速不是为了快，是为了「停不干净就别发下一问」。两条流共用一只 Chat 的 status，会互相拨回去。
  • 以为 transient data part 会进历史。它只走 onData，不进 message.parts；本机实验用 readUIMessageStream 读完，parts 里只剩 text。要进历史就得用普通 part 或 tool part。
