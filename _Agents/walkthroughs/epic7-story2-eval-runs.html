01 · 结论与边界

这一格只做「跑起来」，不做对照与判答

7.2 的成果是一条可复现的执行链：数据集 × 运行配置 × 测评配置 → 一条 run → 逐条 recall/MRR。基线与答案评测还在后面。

01 / SNAPSHOT

POST 时冻结输入

题集逐条（含 gold）、两份配置、embedding 模型/维度、语料计数一次复制进 snapshot jsonb。之后改题集或配置，历史 run 的含义不变。

02 / QUEUE

进程内单队列

一次只跑一个 run，后来的排队；排队中可直接取消，运行中在 case 之间中止（检索本身没有 signal）。队列不持久化，重启由启动清扫把 queued/running 标 cancelled。

03 / RESULTS

逐条写进 jsonb

每条结果 {case_key, rank, matched, total, hit_count, recall, mrr, missing_gold, duration_ms, error} 追加进 results；聚合读取时算，不落第二份。

04 / SAME RETRIEVER

复用生产检索

不另写检索：给 SearchOptions 加四个覆盖位，run 用快照参数调同一只 RetrieverHandle.retriever；/retrieve 不传即保持原行为。

不属于 7.2：基线采纳与并排对照（7.3）、judge / HITL / 答案评测（7.4）、自动回归与 CI 门禁（后续）、vector-only / lexical-only 对比（未排期）、运行删除的 UI（按 Lynx 拍板只做后端端点，入口留 7.3）、跨 run 趋势（未排期）。

02 · 状态与数据形状

一行 run 的五个状态、两个 jsonb

snapshot 是输入，results 是输出；两者都不与外部表 join，历史完全自足。

状态机

  • 创建queued
  • 执行running
  • 结束done / failed
  • 取消 / 重启cancelled

snapshot（输入）

  • cases逐条 + gold
  • configsrun / metric
  • embeddingmodel / dim
  • corpusready / total

results（输出）

  • rank最佳名次
  • matched / totalgold 覆盖
  • hit_count负例看命中
  • missing_gold前缀失效
WHY JSONB

结果不建明细表

读法永远是「打开一次 run，把整份结果拿来看」；15 条规模下，SQL 聚合与 join 换不来什么。jsonb 让一行 run 自带完整历史，删 run 就是删一行。以后真要做跨 run 趋势/筛选再迁移。

WHY OVERRIDES

参数不另造 retriever

检索工厂把阈值/RRF-k 存在构造期；要让每个 run 用自己的参数，可以每 run 造一个带假 AppConfig 的实例，也可以让 search 吃覆盖位。选后者：仍是一只实例，/retrieve 与 run 同源。

03 · 小白词典

读代码前先认识六个词

都是这套执行链的关键名词。

SNAPSHOT

只读副本

不是指针，是当时内容的复制。历史 run 读 snapshot，不回头 join 当前题集/配置表。

QUEUE

进程内队列

一个数组 + 一个 active 标记；重启就丢，所以启动时要把遗留的 queued/running 标成 cancelled。

RRF

名次融合

Retrieval 的 vector 与 BM25 两路按名次相加；run 配置里的 rrf 就是公式里的 k。

recall@k

gold 覆盖率

命中的 gold 数 / gold 总数；部分命中算部分，不判失败。

MRR

名次倒数

最佳命中名次的倒数（1/rank）；没命中记 0。

hit_count

负例的命中条数

负例没有 gold，用原样命中数判断“是不是拒答成功”；0 条才算通过。

13 · 取舍与踩坑

拍过板的、以及会咬人的

这些决定会被 7.3/7.4 直接沿用。

  • 结果放 jsonb，不建 eval_run_cases（Lynx 拍板）：读法永远是整份 run；15 条规模下 SQL 聚合/join 没有收益。代价是跨 run 的趋势/筛选会难受——那属于未排期的趋势图，届时再迁移。
  • 参数走 SearchOptions，不另造 retriever：每 run 造一个带假 AppConfig 的实例能少改代码，但会把“当前检索是什么”变成两份真相；覆盖位让 /retrieve 与 run 始终同源。
  • 队列不持久化，重启靠清扫：OQ-7.2-4 定的是丢排队、标 cancelled。实测：跑一半杀进程，重启日志 I_EVAL_RUN_CLEANUP，run 变 cancelled / 进程重启，已写的 2 条结果保留。
  • 中止只发生在 case 之间：检索没有 signal，硬拆会把「一条 case 跑一半」变成新的状态。取消后的 run 保留已完成行；实测取消 202，最终 cancelled 且 results=1。
  • 单条错误不打死整批：某条检索抛错 → 该行 error + 0 分，run 继续；只有快照参数不合法或执行器自身异常才 failed。这是“失败不自动重试、保留原因”的落点。
  • 删除只做后端（Lynx 拍板）：运行中 409，结束态才允许；删行事务里清 baseline_run_id。7.1 的「先删 N 次运行」现在有 API 出路，UI 入口留 7.3。
  • metric 配置只冻结不执行：7.2 只算 recall/MRR；judge 属 7.4。model / temperature 对检索评测不生效，只记录在快照里。
  • 负例要 hit_count：负例没有 gold，matched/total 是 0/0；没有原始命中数就看不出“拒答成功”还是“碰巧”。本格给结果加了 hit_count。
  • 全局清扫会碰别人的 run：markInterruptedRuns 按设计扫全库；集成测试里加了「库里活跃 run 不是本用例独占就跳过断言」的守卫，避免误伤。
