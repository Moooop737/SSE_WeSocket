01 · 结论与边界

这一格交付什么，不交付什么

5.3 的成果不是“批量上传按钮”，而是把内容身份、两个存储的写入顺序、失败语义和回收路径固定下来。5.2 的归档/ingest/恢复/下载是本格的底座。

01 / DEDUP

内容身份与去重门

SHA-256 小写 hex 作为内容键；resources.content_hash 唯一索引包含软删行；文件/URL/粘贴都在 create 与 MinIO 写入之前查重，命中时两个存储都不写。

02 / VERIFY

客户端预检 + 服务端复核

浏览器算文件 hash、同批预检；服务端不信任请求里的 hash，ingest 对 MinIO 读回的 Buffer 再算一次，不一致直接 E_HASH_MISMATCH。

03 / LIFECYCLE

回收站与重入库

软删行进回收站；彻底删除只接软删行，先删对象再删行并释放 hash；ready 重入库在写入事务里替换旧 chunks/embeddings。

不属于 5.3：批量下载 / ZIP（本轮去掉）、后端任务表 / worker / Redis、批量端点、代码库 ZIP（5.4）、PDF/Word 等新格式、MinIO 薄层子系统（Lynx 2026-10-27 决定之后再做）、硬删审计表（P5）。

02 · 全局地图

两个存储，四个动作

所有正确性都绕着一句话：去重门必须发生在 resources 行与 MinIO 对象写入之前。命中时两边都不写，未命中才 create/put。

前端：先把内容变成 hash

  • 文件原始字节sha256File
  • 同批同 hash队列内已存在
  • 阶段一create / PUT / restore
  • 阶段二POST /:id/ingest

服务端：先查 hash，再决定写不写

  • 文件content_hash 必填
  • URL / 粘贴服务端算 hash
  • 命中 active200 duplicate
  • 命中软删200 restored

存储与生命周期

  • DBresources 行
  • 对象MinIO kbfile
  • 删除软删 → 回收站 → purge
  • 重入库ready → processing

失败也有归属：建行前拒绝不带 resource；建行后失败留 upload_failed/process_failed；ingest 的 hash 不一致不算“对象没上传”，而是内容完整性失败。

03 · 小白词典

读代码前先对齐六个词

这几个词在这页反复出现，先用人话钉住。

SHA-256
内容指纹，不是加密。同样的字节永远得到同样的 64 位小写 hex；改一个字节就会变。
presigned PUT
后端签一个带时效的上传地址，浏览器拿着它把文件直传 MinIO，字节不经过后端。
软删 / 回收站
只给行写 deleted_at，保留 MinIO 原对象；回收站能看到、能恢复，也能彻底删除。
去重门
先算 hash、查库；命中就不建行、不签 PUT、不写对象。它是两个存储写入前的闸门。
两段式
阶段一所有项完成归档/直传，阶段二才开始 ingest；不是服务端队列，刷新页面队列就丢。
FOR UPDATE
PostgreSQL 行锁。写 chunk 前锁住 resources 行，让同一资源的并发重入库排队，避免两份 chunks。

去重键：列、约束与唯一索引

hash 是内容指纹；唯一索引是并发下的最终裁决者。

CORE · 04

前端两段式：先全部归档，再统一 ingest

浏览器算 hash、同批预检；阶段一只做 create/上传/归档，阶段二才 ingest。

这不是后台队列：队列仍是 React 内存数组，刷新即丢；没有任务表、worker、Redis 或批量端点。两段式只是把同一批的提交顺序固定下来。

07 · 取舍与踩坑

为什么是这些形状

每一条都能在上面的代码里找到落点；这里讲被否掉的方案和容易踩的坑。

DECISION 01

去重门放在两个存储之前

不是“先上传再查重”。文件是 presigned PUT 直传，后端在归档时看不到字节；所以浏览器先算 hash，POST 时先查库。命中时 DB 和 MinIO 都不写，省带宽也省清理。

DECISION 02

客户端 hash 只当预检键

请求体里的 hash 可被 curl 改，前端也可能算错。服务端不信任它：ingest 从 MinIO 读回字节再算一次。改 hash 能绕过去重，但绕不过完整性，最终 process_failed。

DECISION 03

两段式，不是后台队列

阶段一全部归档/直传，阶段二统一 ingest；队列仍是内存数组，不建任务表/worker/Redis。刷新页面队列就丢，这是明确的范围边界。

DECISION 04

回收站用独立端点

没有给 GET /resources 加 deleted 过滤。活动列表、状态计数、分页保持“库里有什么”的语义；软删行单独走 /resources/deleted，也方便以后加审计/保留策略。

  • active 命中不救失败行：第一次上传留下 uploading/upload_failed 行时，再传同内容只会命中它并提示；要先彻底删除（回收站）或走后续重试策略，不能指望队列自动重传。
  • 软删行仍占 hash：同内容上传会恢复原行，而不是新建；这是唯一索引包含软删行的直接结果，想真正重传必须先 purge。
  • Web Crypto 需要安全上下文：localhost / HTTPS 可用；普通 HTTP 局域网拿不到 subtle，当前直接报错，没有 JS SHA-256 兜底。
  • 并发重入库会留下两份 chunks：chunks 没有 (resource_id, chunk_index) 唯一约束；没有 FOR UPDATE 时两个事务各自删旧插新，最终各插一份。行锁是这里的正确性来源。
  • 测试夹具顺序变过：两文件用例从“上传 A → 入库 A → 上传 B”改成“上传 A → 上传 B → 入库 A → 入库 B”，因为两段式是契约变化；不是测试迁就实现。
  • purge/restore 还有极小并发窗口：purge 先删对象再删行；若同一行在这两步之间被 restore 抢先，可能“已恢复但对象已删”。单用户下几乎不可见，已记 deferred，待用行锁事务收口。
