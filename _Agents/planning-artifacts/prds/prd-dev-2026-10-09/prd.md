# PRD: Knowledge Copilot
*工作名，正式命名待定（见 §9.2 OI#1）。*

## 0. Document Purpose

本 PRD 面向 PM 本人（Lynx），以及下游的架构 / UX / epics 工作流负责人。它定义 **Knowledge Copilot** 的产品意图：一个从"喂文档做检索问答"起步、按阶段逐步长成的知识研究助手。文档以 Glossary 锚定统一词汇，功能按 feature 分组、FR 内嵌并全局编号，推断处以内联 `[ASSUMPTION]` 标注，并在 §10 汇总。

本次 PRD **重点钉死 P1 的 MVP 范围**（§6），同时用 §7 记录 P2–P5 的能力路线图作为扩展愿景。技术选型、文档格式全菜单等实现层材料见同目录 `addendum.md`，不并入本文。此 PRD 是新建，无既有 UX 或需求文档承接。

## 1. Vision

Knowledge Copilot 是一个**对话式的个人知识库助手**：你把自己收集的资料（先是网页链接和 Markdown/纯文本笔记）喂进去，之后就能用自然语言向这批资料提问，它基于检索到的原文生成回答，并**逐条标注引用来源、可点回原文**。它解决的核心痛点是——收藏了一堆东西却用不起来，找信息时只能靠关键词翻。

这个产品的独特之处在于它的**成长路径**：它不是一次性做完的玩具，而是一个能力阶梯。P1 打通 RAG 检索问答与流式交互；随后依次叠上结构化输出、工具调用 / Agent、生成式 UI（Generative UI，回答里直接渲染图表卡片）、乃至 MCP 与多模态。每一步都为下一步留好接口。

对项目所有者 Lynx 而言，它同时是一台**Vercel AI SDK 的学习载体**：每一阶段都对应 AI SDK 的一类核心能力，做完即沉淀为一个能写进简历、且能持续迭代的作品集项目。用户价值与学习目标在这里是同一条线——产品越长大，练到的能力越深。

## 2. Target User

### 2.1 Jobs To Be Done

- **功能**：把散落的网页/笔记变成一个能用大白话提问的知识库，快速找回"我到底在哪份资料里看过这个"。
- **功能**：得到**有出处**的答案，能一眼核对原文、判断可信度，而不是接受一段无从验证的模型生成文字。
- **情感**：作为 builder，"我用这个产品一步步吃透 Vercel AI SDK"——看着它随自己能力一起长大。
- **社交/职业**：最终产出一个可演示、可写进简历、能讲清技术取舍的作品集项目。
- **场景**：个人研究、学习资料复盘、为自己正在做的项目攒一个随身问答助手。

### 2.2 Non-Users (v1)

- 需要团队协作、共享知识库、权限分级的团队用户。
- 需要多租户 / 账号体系的对外产品用户。
- 追求生产级 SLA、并发与成本优化的线上服务方。

> 以上在 P1 明确排除；是否/何时纳入由后续阶段愿景决定（见 §7）。

### 2.3 Key User Journeys

> 单人自用产品，旅程以"项目所有者 Lynx 本人"为原型主角。

- **UJ-1. Lynx 把一篇网页文章变成随时能问的资料。**
  - **主角 + 情境：** Lynx，正在研究一个新主题，浏览器里开了十几篇文章，记不住哪篇讲了什么。
  - **入口状态：** 本地已启动应用，无需登录（单人自用）。落在"知识库"界面。
  - **路径：** 粘贴一个文章 URL → 点"加入知识库" → 系统抓取正文、切块、向量化 → 资料出现在知识库列表中，状态"已就绪"。连加几篇同类文章。
  - **高潮：** 切到问答框，打一句"这篇文章里提到的三个关键结论是什么？" → 回答逐字流式出现 → 每个结论后面挂着引用标记，点开可看到对应原文片段与来源 URL。Lynx 立刻确认答案有出处。
  - **收尾：** 继续追问细化，资料沉淀为可复用的个人知识库。
  - **边界情况：** 若某 URL 入库失败（不可访问 / 内容为空），列表中以 `失败` 状态呈现该来源，系统明确告知原因，不影响其余资料，也不基于缺失内容编造答案。

- **UJ-2. Lynx 向自己的笔记要一个带出处的总结。**
  - **主角 + 情境：** Lynx 有一堆 Markdown 读书笔记，想快速回顾某个主题但不想逐篇翻。
  - **入口状态：** 笔记文件已在本地。
  - **路径：** 上传/粘贴 Markdown → 入库 → 提问"关于 X 主题，我的笔记里都记了哪些点？"。
  - **高潮：** 回答聚合多篇笔记内容、流式给出，并逐条引用到具体笔记与段落。
  - **收尾：** 得到一份可核对的回顾，无需重读原始笔记。

## 3. Glossary

> 下游流程与读者必须严格使用以下术语，全文不得引入同义替换。

- **知识库（Knowledge Base）** — 当前唯一用户（单人自用）所有已入库 Resource 的集合及其检索索引。
- **资源（Resource）** — 一份被抓取或导入并解析的原始资料（一个 URL、一个 .md、一段 .txt）。是引用归属的最小单位。
- **抓取（Fetch）** — 从在线 URL 拉取正文内容的动作。
- **入库（Ingest）** — 将 Resource 解析、切块、向量化并写入知识库的完整过程。
- **分块（Chunk）** — Resource 切分后的检索单元；一个 Resource 含一到多个 Chunk。
- **向量化（Embedding）** — Chunk 的向量表示，供检索使用（相似度为其中一种检索实现）。
- **检索（Retrieval）** — 依据提问从知识库中找出相关 Chunk 的过程；实现可为向量相似度、BM25 全文或二者混合，由架构阶段定，但引用归属须以最终命中的 Chunk 为准。
- **回答（Answer）** — 模型基于检索到的 Chunk 生成的流式文本。
- **引用（Citation）** — Answer 中标注其依据来源的标记，指向具体 Resource/Chunk。
- **原文回链（Source Ref）** — 用户从 Citation 点回原始内容（URL 片段或笔记段落）的跳转能力。
- **会话（Session）** — 一次多轮问答的上下文容器（P1 至少支持单会话内多轮）。
- **资源状态（Resource Status）** — Resource 在入库过程中的生命周期标记；P1 取三态：`处理中`（抓取/解析/向量化进行中）、`已就绪`（可被检索命中）、`失败`（Resource 已创建但后续任一步失败，含不可访问、内容为空、解析/向量化失败，附原因）。边界：输入校验失败（非法 URL、空内容、非 P1 支持类型）**直接拒绝、不创建 Resource**；已进入入库后才失败才转 `失败`。重启后仍处 `处理中` 的 Resource 转为 `失败(入库中断)`，不长期悬挂。（注：本枚举指 Resource 入库状态，与 FR-9 的"请求 Loading"无关。）
- **Provider** — 提供 LLM / Embedding 能力的服务商，经 Vercel AI SDK 抽象层接入，可替换。

## 4. Features

### 4.1 知识入库（Resource Ingestion）

**描述：** 用户把网页 URL 或 Markdown/纯文本**添加**进产品，系统完成抓取/读取、解析、分块、向量化并写入知识库。这是 P1 的地基——没有可问的资料就没有问答。P1 明确只支持这两类来源，其余格式进入 backlog（见 `addendum.md` B）。实现 UJ-1、UJ-2。`[ASSUMPTION: P1 不做文件批量上传，URL 与 Markdown/纯文本逐个/少量添加即可。]`

**Functional Requirements：**

#### FR-1: 添加网页 URL 入库
用户可提交一个网页 URL，系统抓取正文并作为一个 Resource 入库。实现 UJ-1。
**Consequences (testable):**
- 提交有效可访问 URL 后，知识库中出现对应 Resource，状态最终转为"已就绪"。
- 已进入入库后才失败（不可访问 / 抓取为空等）时，创建一个状态为 `失败` 的 Resource（附原因），其余资料不受影响。
- 输入非法（空、非法 URL 格式、非 P1 支持类型）时直接拒绝并提示，**不创建 Resource**。
**Out of Scope:** 需要 JS 渲染才能出正文的页面、有强反爬的站点——P1 仅保证**静态正文**抓取，命中此类来源时系统明确提示"可能抓不全"（OQ#3 决议）。

#### FR-2: 导入 Markdown / 纯文本
用户可粘贴或导入 Markdown / 纯文本内容，系统将其作为一个 Resource 入库。实现 UJ-2。
**Consequences (testable):**
- 导入后 Resource 出现在知识库列表并可用于检索。
- 内容为空、编码异常或不可读时拒绝入库并提示（不创建 Resource）。

#### FR-3: 解析与分块
系统从入库的 Resource 中解析出正文，并切分为一到多个 Chunk。实现 UJ-1, UJ-2。
**Consequences (testable):**
- 每个已就绪 Resource 至少含一个 Chunk；Chunk 保留可回溯到 Resource 的定位信息（粒度到 Chunk 而非仅 Resource）。
- 解析后正文为空/全空白（得到 0 个 Chunk）时，Resource 转 `失败(内容为空)`，不得进入 `已就绪`。
**Out of Scope:** 复杂版面还原、表格/图片解析（属 backlog）。

#### FR-4: 向量化与索引存储
系统为每个 Chunk 生成 Embedding 并写入知识库索引，使其可被检索。实现 UJ-1, UJ-2。
**Consequences (testable):**
- 入库完成的 Resource 的 Chunk 可被后续检索命中。
**已定案（见 §9 OQ#2）：** Embedding 由本地 Ollama 跑 Qwen3-Embedding（1024 维）产出；存储采用 ParadeDB（Postgres 全文 BM25 + pgvector 扩展）。真持久化（数据落库，进程重启后知识库仍在）——细节见 `ARCHITECTURE-SPINE.md`。

#### FR-5: 知识库内容查看与删除
用户可查看当前知识库中的 Resource 列表及其状态，并删除某个 Resource。实现 UJ-1。
**Consequences (testable):**
- 删除 Resource 后，其 Chunk 不再出现在后续检索结果中。
- 删除后，历史 Answer 中指向该 Resource 的 Citation 降级为不可点的纯文本并标注"来源已删除"（不产生悬空/404 引用）。实现 UJ-1, UJ-2。
- 删除处于 `处理中` 的 Resource 时，取消其后端入库任务并清理已产生的部分 Chunk（不留孤儿向量）。

**Notes:** `[NOTE FOR PM] 分块粒度（chunk 大小 / 重叠窗口）与 Embedding 写入成功的判定阈值属实现层，PRD 不写死，由架构阶段决定。`

### 4.2 检索问答（Grounded Q&A）

**描述：** 用户用自然语言提问，系统检索相关 Chunk，并让模型**只依据检索到的知识库内容**生成回答；无法由知识库内容支撑时如实说明，不编造。多轮场景下**事实依据仍仅为 Chunk**，历史 Answer 只作上下文指代消解、不作引用来源。这是产品价值的核心。实现 UJ-1、UJ-2。

**Functional Requirements：**

#### FR-6: 基于知识库检索回答问题
用户提问后，系统检索相关 Chunk 并据此生成 Answer。实现 UJ-1, UJ-2。
**Consequences (testable):**
- 对知识库中有依据的问题，Answer 内容可对应到被检索的 Chunk。
- 检索未命中、或最高相关性低于下限（阈值由架构定）时，视同"知识库中未找到相关内容"并如实说明，不得把低相关噪音当依据作答。
- 知识库为空时，给出区别于"未找到相关内容"的提示（"尚未添加任何资料"）。
- 空/纯空白提问被拒绝并提示。

#### FR-7: 会话内多轮上下文
系统在同一 Session 内保持上下文，允许用户基于前一轮继续追问。实现 UJ-1, UJ-2。
**Consequences (testable):**
- 追问中的指代（如"第二个结论展开讲讲"）能结合上一轮 Answer 正确理解。
- 基于历史轮次的追问，系统需重新检索（先做指代消解/查询改写），而非直接复述上一轮生成文本作为依据。（查询改写策略属实现层。）
`[ASSUMPTION: P1 支持单个活跃 Session 的多轮；不做多会话历史列表管理。]`

**Notes:** `[NOTE FOR PM] 检索 top-K / 相似度阈值等参数属实现层，由架构阶段决定；PRD 只约束"只依据检索到的内容作答、无依据时如实说明"。`

### 4.3 流式交互（Streaming UX）

**描述：** 回答以流式逐字呈现，配合清晰的 **Loading** 状态，长回答不必干等。这是 AI SDK `streamText` 的直接体现，也是 P1 学习重点之一。实现 UJ-1。

**Functional Requirements：**

#### FR-8: 回答流式输出
Answer 以 token 流式增量呈现，而非等待完整结果一次性返回。实现 UJ-1, UJ-2。
**Consequences (testable):**
- 生成过程中 UI 持续显示已产出的部分，无需等全文完成。
- 流式中途断开时，已产出的部分 Answer 显式标为"回答未完整"，其 Citation 仅在对应 Chunk 已完整落地后方可点击（不展示无法解析的半截引用）。

#### FR-9: 请求 Loading 状态可见
提问后到首个 token 前，系统提供可见的 Loading 反馈。实现 UJ-1。
**Consequences (testable):**
- 请求进行中界面有明确状态指示；错误/中断/首 token 超时有可理解的提示（超时有上限）。

### 4.4 引用溯源（Citations & Source Refs）

**描述：** 回答附引用标记，用户可点回原文片段。这是 P1 的"可信度"亮点，也是与普通聊天相比的关键差异。实现 UJ-1、UJ-2。

**Functional Requirements：**

#### FR-10: 回答附引用标记
Answer 中标注其依据来源的 Citation，指向具体 Resource/Chunk。实现 UJ-1, UJ-2。
**Consequences (testable):**
- 有依据的 Answer 至少包含一个可解析的 Citation。
- 每个 Citation 必须映射到**本轮真实检索命中的具体 Chunk**（非仅 Resource 级）；模型自造的索引视为无效。
- 删除某 Resource 后，历史 Answer 中指向它的 Citation 按 FR-5 降级为不可点的纯文本。

#### FR-11: 引用可回链原文
用户可从 Citation 发起 Source Ref 跳转，查看对应的原始内容（URL 定位或笔记段落）。实现 UJ-1, UJ-2。
**Consequences (testable):**
- 点击 Citation 展示与之对应的原文片段或跳转到源位置。
- 对无文件名/无 URL 的粘贴内容，自动生成来源标识（如命名 + 时间/内容指纹），保证 Source Ref 可归属。
`[ASSUMPTION: "回链"最低门槛为展示该 Chunk 的原文片段 + 来源标识（URL/文件名），字符级高亮为增强项。]`

**Notes:** 引用与检索的对应关系是本产品最容易出 bug 的地方，需在实现阶段专门验证。

### 4.5 运行与安全约束（系统级）

**描述：** 单人自用不等于无需考虑暴露面；作品集对外演示时尤其易翻车。本节约束运行环境。实现 §8 SM-5。

#### FR-12: 本地优先的安全边界
系统在默认配置下仅本地监听，不裸露数据与密钥。
**Consequences (testable):**
- P1 默认仅本地（127.0.0.1）监听；Provider API Key 仅存服务端环境变量，不下发前端。
- 知识库内容不默认对外可达；若对外演示，需以只读或临时实例进行。
`[ASSUMPTION: P1 不做多用户隔离/权限分级，仅靠本地监听与只读演示保障。]`

## 5. Non-Goals (Explicit)

Knowledge Copilot 在 v1（P1）**不做**以下事情（面向"它不是什么"的长期边界）：

- 不做多用户、账号、登录、权限或团队协作共享知识库。
- 不做计费、订阅或任何形式的商业化。
- 不做生产级部署、SLA、横向扩展与成本优化。
- 不做模型微调，不做知识库内容的隐私分级/加密。

> 阶段性的延后项（多格式解析、多模态、工具调用/Agent、生成式 UI、MCP 等）统一见 **§7 路线图**与 **§6.2**，不在此重复罗列。

## 6. MVP Scope（= P1）

### 6.1 In Scope
- P1 = §4 的 FR-1 至 FR-12 全部（入库、检索问答、流式、引用溯源、本地安全边界）。
- 单人自用的极简 Web 界面：一个入库/知识库区 + 一个问答区。
- 默认经 AI SDK 接入：Embedding=本地 Ollama Qwen3；对话=DeepSeek / 百炼（可切换；见 §9 OQ#2）。

### 6.2 Out of Scope for MVP（仅列 MVP 特有延后项）
- 多会话历史管理、持久化用户数据 → 视需要 P2+。
- "字符级高亮的原文回链"（FR-11 增强项）→ 延后。
- 多格式解析（PDF 等）/多模态/结构化输出/Agent/Generative UI/MCP/部署 → 见 §7 阶段划分（不在 MVP）。
- 账号系统、协作、计费 → 非目标（见 §5）。

> **P1.x 界定**：本文所称 P1.x = MVP 验收通过后的追加，**不属于 P1 完成条件**（避免被读成"P1 期间顺手做"而撞 SM-C2）。

## 7. 分阶段能力路线图（Progressive Capability Roadmap）

> 本产品定义的扩展性内核。P1 之后，产品沿下列阶段持续长大；每阶段绑定一类 Vercel AI SDK 能力。此处仅记录愿景，各阶段 FR 在对应阶段更新本 PRD 时展开。技术映射细节见 `addendum.md` C。

- **P1（本文档范围）** RAG 检索问答 + 流式 + 引用 —— `streamText` / embed。
- **P2** 多轮会话管理 + 结构化输出 —— 会话状态、`generateObject`。
- **P3** 检索/联网升级为"工具"，引入 Agent loop —— tool calling、agents。
- **P4** 回答内渲染图表 / 交互卡片 —— `streamUI`、React Server Components（简历亮点；对前端选型有约束，见 `addendum.md` A）。
- **P5** MCP 集成 + 多模态输入（图片/音频入库）+ 部署上线 —— MCP client、multimodal、生产部署。

设计意图（而非硬约束）：P1 实现时应避免把检索策略硬编码进生成路径，以便 P3 能将其工具化；具体解耦与接口方式由架构阶段决定。

## 8. Success Metrics

> 学习 + 作品集项目，指标以"是否真在用、是否真练到、是否拿得出手"为主，不追求线上业务量级。

**Primary**
- **SM-1**：使用留存 — Lynx 每周实际用它查询资料 ≥ 2 次，且 P1 完成一个月后仍在用（未弃坑）。验证 FR-6, FR-8, FR-10。

**Secondary**
- **SM-3**：入库成功率 — **符合 P1 抓取范围的来源**（静态正文可达、非登录/非 JS-only）中，成功入库并转为"已就绪"的比例 ≥ 80%；被排除类来源不计入分母（单列"明确告知不支持"）。验证 FR-1, FR-2, FR-3, FR-4。
