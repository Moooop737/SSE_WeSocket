Trace 耦合关系：编译期与运行期

结论：业务模块只 import bridge，不 import OTel；运行期靠 5 个进程级全局状态 + 2 个 Map + 两套 ALS 关联到一起。 下面两张图分别说明「谁依赖谁」和「请求期间数据怎么流动」，每个块后面有逐条解释。

local_trace_id · UUID 端点壳生成，写 traces.id、pino 日志、X-Trace-Id。覆盖所有请求，包括非 LLM 路由。
OTel / Langfuse trace_id span 创建后才存在，最后由 takeChatTraceId 回填到 traces.langfuse_trace_id。只有 LLM 调用才有。
sessionId 业务会话 id，映射到 Langfuse 的 session.id，用于把多轮对话归到同一个 session 下。

02

运行期关联：5 个全局单例 + 两套 ALS

这张图是请求真正跑起来后的数据流：谁写 Map、谁读 ALS、trace id 从哪来、又回到哪去。

全局 TracerProvider global

trace.setGlobalTracerProvider(provider) 是进程级单例。所有 OTel span——AI SDK 的根/步/模型 span、startObservation 的 stage span——都从这里出。

它挂了两个 processor：LangfuseSpanProcessor 负责导出，ChatSpanProcessor 负责关联。

全局意味着：谁再调一次 setup 就会把它换掉；测试里误调会让整个进程开始导 span。

全局 ContextManager global

AsyncLocalStorageContextManager。没有它，OTel 的「当前 span」跨不了异步边界，stage span 挂不到父 span 下。

它和 pino ALS 不是一个东西：前者管 span 父子，后者管日志字段。

registerTelemetry global

AI SDK 的进程级 integration 注册表。注册 LangfuseVercelAiSdkIntegration 后，每次 generateText/streamText 的生命周期事件都会发给它，由它建 span、导出。

chat.ts 里传的 functionId: 'chat' 会被 @ai-sdk/otel 写成 gen_ai.agent.name = "chat"——这就是 ChatSpanProcessor 用来认「这是 chat 根 span」的记号。

@ai-sdk/otel/dist/index.js:768

pino ALS 关联键

本地 UUID 的家。端点壳写入，日志 mixin、DB stage sink、ChatSpanProcessor 都从这里取。

流式回调（onError/onEnd）跑在请求作用域外，所以 chat 用 withTrace(TraceId, ...) 把回调重新包回同一个 ALS。

Chats Map 入口方向

本地 UUID → sessionId。beginChat 在 streamText 前写，ChatSpanProcessor 在根 span 启动时读，takeChatTraceId 在流结束时删。

为什么需要：OTel span 不知道 sessionId，而 sessionId 是业务才知道的。

失败模式：流异常到 onEnd 都没跑，这条映射会留在内存里（量小，但不清理）。

TraceIds Map 出口方向

本地 UUID → OTel trace_id。由 ChatSpanProcessor 在根 span 启动时写，takeChatTraceId 在 onEnd 读并删。

为什么需要：trace id 是 span 创建后才生成的，业务/数据库当时还不知道。

两个 Map 方向相反：一个把业务信息送进 span，一个把 span 信息送回业务。

ChatSpanProcessor.onStart 接缝

只处理根 span（无 parentSpanContext 且 gen_ai.agent.name === 'chat'）：

  • 从 pino ALS 取本地 UUID；
  • 用 UUID 查 Chats 得 sessionId；
  • 往根 span 写 trace 级属性：session.id、traceName='chat'、tags=['chat']、metadata.route、metadata.local_trace_id；
  • 把根 span 的 OTel trace id 写进 TraceIds。

onEnd 空着，shutdown/forceFlush 也空着——导出 flush 归 LangfuseSpanProcessor。

src/trace/llmtrace/langfuse.ts:85-111

根 span / AI SDK spans 观测

由 Langfuse integration 通过 @ai-sdk/otel 创建：一次生成一个根 span，下面有步骤 span、模型调用 span。

runtimeContext（若配了白名单）只会作为 observation metadata 挂在 span 上；trace 级属性只有 ChatSpanProcessor 写的那几个。

onEnd + withTrace 业务收口

不是 span，是业务收口：流结束后补 traces 行的耗时/状态/错误码；takeChatTraceId 取 Langfuse trace id 回填；落 assistant 消息。

必须放这个回调里，因为只有它拿得到 responseMessage / isAborted / isCancelled / outcome。withTrace 只为让里面的 logError 带上 trace_id；finishTrace 本身不需要 ALS，因为 TraceId 是显式参数。

src/agent/chat/chat.ts:94-134

retrieve → stage sink 工具侧

工具执行时从 bridge 取 sink，Retriever.search 里的 stage runner 每段调 sink.record。

Langfuse 版 sink 用 startObservation 开 span，并声明 embedTelemetry: 'on'（让检索里的 embedding 也进 Langfuse）；DB 版 sink 声明 'off'，避免重复 trace。

这个位置 runtimeContext 到不了，所以必须走 bridge / 闭包。

traces 行 持久化

本地真源：id 是本地 UUID，session_id 由 setTraceSession 写，langfuse_trace_id 由 onEnd 回填。

两个 ID 都存，因为互相推不出来：本地 UUID 覆盖所有请求（包括非 LLM），OTel id 只有 LLM 调用才有，且生成权在 OTel 手里。

03

耦合到底在哪

四个层次，从编译期到运行期逐层加深。

层次内容runtimeContext 能改吗
编译期 业务只 import bridge.ts，实现倒置；测试不加载 OTel / Langfuse。 不能，它不改变模块依赖
全局状态 TracerProvider、ContextManager、registerTelemetry 注册表、bridge 模块变量、两个 Map。 不能，它进不了这些单例
关联键 本地 UUID 串 DB/日志，OTel trace id 串 Langfuse，sessionId 串业务；ChatSpanProcessor 是唯一同时摸到三方的地方。 只能补一块：observation metadata
时序与契约 setupLangfuse 必须在请求前；functionId='chat' 与 gen_ai.agent.name 是隐式契约（常量放 bridge 里就是为了不写两份）。 不能，它不参与启动时序
runtimeContext 的边界

它能做的：作为 observation metadata 出现在 Langfuse 的根/步/模型 span 上（需要 includeRuntimeContext 白名单）。它做不到：写 trace 级 session.id / traceName / tags、回传 OTel trace id、进入工具 execute、进入 ChatSpanProcessor。所以它只能补旁路，替不掉 trace 桥。
